# MimicでUIを改善する

非デザイナーが伝えた違和感から、対象の目的と課題を理解し、文脈に合う変更を選んで適用し、結果を確かめるためのAI向け手順です。「この画面、なんか使いづらい」から始められます。

## 1. 対象と目的をつかむ

相談の対象を特定し、読める仕様・コード・画面や既存の利用記録を調べます。誰が、どの状況で、何を終えようとして、どこで止まったかを整理します。利用者の目的、改善で守る条件、観察できた事実、原因の仮説を区別します。画面や実装が見られなければ、判断に必要な最小限の資料を頼みます。

## 2. 改善案が変わる前提を掘り下げる

[困り方から調べる索引](symptoms.md)から複数の原因候補を挙げ、どの事実で見分けられるかを考えます。人に聞く前に、対象を自分で操作したり、実装やログを調べたりします。

判断が分かれる問いを一巡ごとにまとめます。各問いに理由と仮の見立てを添え、本人が経験から答えられる言葉で尋ねます。「どのデザイン原則に反していますか」より「押す前と押した後のどちらで止まりましたか」のように聞きます。返答を受けて見立てを更新し、次の判断に必要な問いへ進みます。本人に理由が分からなければ、一度操作してもらう、AIが再現して仮説を出す、小さな比較案を試すなど、手掛かりに合う方法を選びます。改善案が変わる前提について、答えが得られるか、何を試せば判断できるかが明らかになるまで続けます。

## 3. 知識を選んで適用する

[知識の索引](../knowledge/README.md)や[関係グラフ](../relations/README.md)で候補を探し、使う本文・版・対象範囲・出典対応表を読みます。判断の根拠にする原典の該当箇所も確かめます。候補ごとに適用条件と、条件が外れた場合の限界を対象の事実と照合します。

目的と制約に照らして案を選び、相談で求められた設計案、試作または実装へ反映します。重要な前提が未確定なら、その前提と確かめ方を示し、許可された範囲で可逆な試案を扱います。既存のデザインシステムや製品の指示、実装の権限を尊重します。本文や出典を取得できない場合は、読めた範囲を伝え、出典を確かめた判断として扱いません。

## 4. 結果を確かめ、記録の要否を決める

変更前の課題に対応する課題を用意します。AIは再現できる入力や状態を使い、動作・表示・アクセシビリティなど、検査できる条件を実際に確かめます。人が完了できるか、何が起こったと理解するか、迷いや不安が減ったかは、その人の操作または短い感想から判断します。操作方法を教えず、たとえば「この変更は保存されたと思いますか」と尋ねます。人による確認ができなければ、効果は未確認と報告し、次に一度試せる課題を添えます。[保存の作例](saving-example.md)

報告には、対象の目的、選んだ変更と理由、読んだ本文と版・出典、実際に確かめたこと、未確認事項を含めます。記録の指定がなければ、会話で完結するか、利用側のPRや設計資料に要点を残すかを状況に応じて勧め、ファイルを作る前に利用者の選択を聞きます。[適用契約](https://github.com/9uiLe/mimic/blob/main/contracts/README.md)は、対象条件や証拠を構造化する必要がある場合に使えます。複数の状況に通用する理由と条件を説明できる知見は、個別の記録とは別にMimicへの収録を提案できます。
