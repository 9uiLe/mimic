# インタラクションデザイン

## 概念

インタラクションデザインは、利用者の行為と、それに対するシステムの応答を通じて、製品の振る舞いを考える領域です。
この本文では、何ができるか、何が起こったか、次に何ができるかというつながりを扱います。
画面を移る場合に加え、同じ画面の表示や操作可能な内容が変わる場合も含みます。

たとえば保存ボタンの見た目だけでは、保存が始まったのか、完了したのか、失敗して入力が残っているのかは決まりません。
この説明用の例では、利用者の操作と、処理の状態と、伝える内容を結び付けることが問題になります。

## 背景と資料の立場

本項目は、一つの理論の分類を紹介するのではなく、Appleのナビゲーション・フィードバック・モダリティ・プライバシーの指針から説明します。
Appleの指針は同社のプラットフォームを対象とする設計上の立場です。
Webにおける入力エラーとステータスメッセージの要件は、W3CのWCAG 2.2から範囲を限定して参照します。

[情報アーキテクチャ](../information-architecture/KNOWLEDGE.md)が情報や機能の構造を扱うのに対し、ここでは人がその構造を使って行為を進める際の応答を扱います。
利用の前後や複数の接点を含む経験の流れは、[ユーザージャーニー](../user-journeys/KNOWLEDGE.md)で読むことができます。

## 画面の役割、階層、戻り方

画面を区別する際には、場所の名前に加え、そこで読む、選ぶ、編集するなどの役割を考えます。
AppleのiOS向け解説は、階層の詳細へ進む遷移と、独立した作業を扱うモーダル表示を区別しています。
階層のナビゲーションでは、タイトルや戻るラベルが、現在地と戻る先を知る手掛かりになります。

モーダル表示は親の表示への操作を一時的に止め、別の作業へ注意を向ける方法です。
Appleは、明確な利点がある場合に使い、作業と閉じ方を分かるようにすることを勧めています。
元の作業へ戻るためにも、モーダル内での移動と、モーダル自体を閉じる操作は読み分けられる必要があります。

「戻る」「取り消す」「保存して閉じる」は、同じ場所へ移る場合でも、入力に対する結果が異なり得ます。
これは振る舞いを区別するための説明であり、すべての製品に同じボタンを追加する指示ではありません。
Appleのモダリティ指針は、閉じると作成内容を失う場合に、状況と解決方法を伝えることも扱います。

## 状態とフィードバック

フィードバックは、現在の状況、操作の成否、次に取れる行為を利用者へ伝えます。
Appleは、内容の重要さに応じて伝達方法を選び、通常の状態情報と重要な警告で中断の強さを変える考え方を示しています。
すべての変化をアラートにすることや、すべての成功に確認画面を出すことを意味しません。

| 説明用の状態 | 区別して考える内容 |
| --- | --- |
| 空 | 対象がまだないのか、検索条件に一致しないのか。これからできることは何か。 |
| 処理中 | 操作を受け付けたか、まだ待つ必要があるか。別の操作や中断が可能か。 |
| 完了 | 何が完了し、結果をどこで確認できるか。追加操作が必要か。 |
| 失敗 | 何が起こらず、どの内容が残っているか。修正や再試行が可能か。 |

この表は、正常な結果だけに説明を限定しないためのMimicの整理です。
四つで全状態を網羅する分類や、状態機械という実装方式の指定ではありません。
状態を表す言葉、表示内容、操作の結果が食い違わないことを、個々の作業に沿って考えます。

## 中断、再開、利用者の制御

行為のつながりは、画面が開かれ続ける場合だけではありません。
別の場所を見て戻るときや、作業をいったん閉じるときにも、どこまで進んだかと、何を続けられるかが関わります。
AppleのiOS向け解説は、タブを切り替えても各階層の文脈を保つことを扱います。
作業中断後の保存内容や再開位置は、これを手掛かりに個別製品で定める事項です。

また、利用者が操作を選べることには、データや機器へのアクセスを許可するかどうかも含まれます。
Appleのプライバシー指針は、必要なデータだけを求め、必要になる文脈で用途を明確に説明することを勧めています。
許可要求は操作の前提や分岐に関わるため、成功時の画面から切り離さずに考えます。
この本文は、同意や保存期間の具体仕様、法的な適合判断までは定めません。

## アクセシビリティと適用範囲

応答は、画面を見ている人だけへ届けばよいとは限りません。
Appleは、複数の方法でフィードバックを伝え、VoiceOverなどを使う人も受け取れるようにすることを勧めています。
WCAG 2.2は、検出した入力エラーの対象と内容をテキストで示すことや、ステータスメッセージを支援技術が扱えることを定めます。
これらのWebの達成基準を読んだだけで、ネイティブアプリの適合や使いやすさを証明したことにはなりません。

画面遷移図や状態の表は、意図した振る舞いを説明できますが、実際の理解や操作を確かめた結果とは区別します。
個別UIを確かめる観点は[ユーザビリティテスト](../usability-testing/KNOWLEDGE.md)で扱います。
