# C4モデルとアーキテクチャ図

## 概念と背景

C4モデルは、Simon Brownがソフトウェアの構造を伝えるために作った、抽象度を段階的に変えて図を読む方法です。
対象システムと周囲の関係から、その内部のアプリケーション、構成要素、コードへと範囲を絞ります。
設計中の説明にも、既存システムの理解や引き継ぎにも使います。

C4は、記号や描画ツールを一つに固定する規格ではありません。
箱の形だけをそろえるよりも、何を一つの要素とし、どこまでを一枚で説明するかをそろえることが中心です。
全段階を作成する義務はなく、公式解説は多くのチームではSystem ContextとContainerで足りるとしています。

## 図の種類と使い所

| 図 | 答える問い・資料での使い所 | 作成のポイント |
| --- | --- | --- |
| System Context（システムコンテキスト図） | 誰が使い、何と連携するか。企画の共有、担当範囲の確認、導入説明 | 対象システムを一つの要素にし、利用者と直接関わる外部システムを置く。内部のAPIやDBを混ぜず、利用・連携の目的を記す |
| Container（コンテナ図） | アプリケーションやデータストアが責務をどう分担するか。基本設計、技術レビュー | システム境界を開き、各要素の責務・技術・通信方式を記す。WebアプリとDBなどの関係を示す |
| Component（コンポーネント図） | 一つのContainerの内部をどう分けるか。詳細設計、変更影響の説明 | 対象Containerを一つ選び、内部要素の責務と依存を示す。外部との接点も残し、全システムの細部を詰め込まない |
| Code（コード図） | 特定Componentをどう実装するか。複雑な部分の検討 | クラスなど、論点に必要な要素に絞る。長期保守ではIDEなどからの生成も検討する |
| Deployment（配置図） | 実行・保存単位のインスタンスがどこで動くか。環境構築、運用・障害対応 | 本番・検証など環境を指定し、配置ノードとインスタンス、必要なネットワーク機器を示す |
| Dynamic（動的な相互作用の図） | 一つの機能で要素がどの順に協調するか。複雑な連携の説明 | 静的な構成図と同じ要素名を使い、対象シナリオを絞る。やり取りに順序を与える |

先頭の四つが、C4の名前の由来になる静的構造の段階です。DeploymentとDynamicはそれを補助する図です。
表の資料名は、公式の対象範囲を開発作業へ対応させたMimicの説明上の整理です。

## 描き分けるポイント

C4のContainerはアプリケーションやデータストアを表し、Dockerコンテナと同義ではありません。
一つの論理的なアプリケーションが本番では複数台に配置されることもあります。
その責務をContainer図で、具体的な配置・複製を環境ごとのDeployment図で説明します。

タイトルに図の種類と対象範囲を入れ、要素には種類・名前・短い責務を添えます。
ContainerやComponentでは技術も示します。
矢印には方向に合う関係名を付け、「使用する」だけで済ませず、何を要求・保存・取得するかを記します。
Container間の通信にはHTTPなどの方式も添えます。

線種、矢印、囲み、色の意味は凡例で説明します。
図を分けても要素名を統一し、下位の図でどの上位要素を展開したか分かるようにします。
静的な依存関係を示す線から、呼出し順序や処理時間を読み取ることはできません。

## 作成手段と保守

議論中はホワイトボードでも表現できます。保存する資料では、編集する人、読者の閲覧環境、差分確認、更新期間を考えてツールを選びます。
図ごとに箱を複製する方法と、共通モデルを定義して複数の図を取り出す方法は異なります。
後者は要素名や関係の一括更新に向きますが、モデルの管理が必要です。

Mermaidの汎用フローチャートでも簡略な構成図は描けますが、C4の抽象度や責務をツールが自動保証するわけではありません。
[注文システムの説明例](examples/order-system.md)に、同じ対象をContextとContainerで描き分けるソースと読み方を示します。

## 関連概念と対象範囲

[UML](../uml/KNOWLEDGE.md)は構造や振る舞いを記述するモデリング言語で、C4はアーキテクチャを説明する抽象度と図の範囲を整理します。
C4のCode図にUMLクラス図を使うなど、両者は組み合わせられます。
構成図に処理分岐を詰め込む代わりに、相互作用の詳細はシーケンス図などへ分けて説明できます。

C4図がそろうことは、設計の妥当性や可用性、性能、セキュリティが検証済みであることを意味しません。
図は対象と関係を共有する表現であり、設計の理由、制約、測定結果は対応する文章や記録で補います。
