# プロダクトの設計判断と知識の適用契約

プロダクト全体のUI/UXを考える入口は[設計判断台帳のモデル](product-design.md)です。目的・利用状況・対象範囲から必要な判断を登録し、その判断に使う知識・制約・共通方針と確認を結び付けます。デザインシステムや形式化済み契約の存在を、判断の登録条件にしません。

適用契約は、知識を使う対象・前提・満たすべき状態・判定に必要な証拠を定義します。概念の説明とは独立した、Mimicによる操作的な解釈です。同じ概念から、対象範囲の異なる複数の契約を作れます。一つの契約が複数の概念を参照することもできます。

知識の意味と出典は引き続き [knowledge/](../knowledge/README.md) が所有します。適用契約は原典そのものでも、新しいデザイン理論でもありません。契約の採用、実際の適用、条件の充足を別々に扱います。

## 三つの提供形式

| 利用者・用途 | 入口 | 内容 |
| --- | --- | --- |
| 人が設計と保証範囲を理解する | [製品全体の判断モデル](product-design.md)と[契約の仕様](model.md) | 対象と判断、知識との違い、判定の意味、形式化の境界 |
| AIが契約を選び、証拠を集めて判断する | [AI向け利用手順](agent-guide.md) | 参照、対応付け、未確定時の扱い、報告 |
| AIの検査プログラムや判断基準へ組み込む | [台帳スキーマ](schemas/product-design.schema.json)、[契約スキーマ](schemas/contract.schema.json)、[評価記録スキーマ](schemas/assessment.schema.json) | 判断の参照関係、型付きの条件、意味判断の基準、来歴と結果 |

三つの形式は、同じ契約ID・版・要件IDを使います。数値や条件の定義元は契約JSONであり、文書へ別の規則として書き写しません。知識本文をAI向けに要約し直したものを、第二の説明正本にしません。

台帳の対象種類と論点は開いた語彙です。例の列挙をUI/UXの完全分類にせず、目的を決める判断、情報・機能・操作・状態・内容・表現・接点など、案件で必要な判断を登録できます。未契約・未決定・未確認も残し、宣言した範囲の確認と未知のUI/UXの網羅性を区別します。

## 正本と実行記録

```text
knowledge/<id>/KNOWLEDGE.md       概念の説明正本
relations/                      概念間の索引
contracts/
  README.md                     人向けの入口
  product-design.md             製品全体の対象範囲と判断台帳の意味
  model.md                      データと判定の意味
  agent-guide.md                AI向け利用手順
  schemas/
    product-design.schema.json  案件の設計判断台帳の構造
    contract.schema.json        再利用する適用契約の構造
    assessment.schema.json      対応付け・証拠・結果の構造
  definitions/*.json            適用契約の定義元
  examples/                     架空の入力・期待結果
output/contracts/<run-id>/      実案件の評価記録。Git管理外
```

契約は対象の選び方と条件を所有します。評価記録は案件側が所有し、成果物の版、対象要素、表示条件、観測、判断理由を持ちます。実行結果を契約定義へ保存しません。既存の関係グラフは索引のまま保ちます。

案件の台帳は対象と判断の母集合を所有し、契約評価や観察結果を参照します。契約がない判断を索引から消したり、共通部品に当てはまらない判断を対象外にしたりしません。

契約の発見には `definitions/*.json` を列挙し、`sources[].concept` で概念IDを探します。契約がない概念は「未定義」です。適用対象外や充足済みという意味ではありません。全知識への契約作成を、知識の掲載条件にはしません。

## 何を判断できるか

| 問い | 記録する状態 | 判断の意味 |
| --- | --- | --- |
| この対象に適用できるか | `applicable`、`not-applicable`、`undetermined` | 根拠のある対象条件と例外の判定 |
| この契約の検査範囲で扱えるか | `supported`、`unsupported`、`undetermined` | 対象に対する、この検査モデルの能力 |
| 判断や変更に使ったか | `recorded`、`not-demonstrated`、`undetermined` | 要件と設計判断を結んだ適用記録の有無 |
| 対象が条件を満たすか | `satisfied`、`violated`、`undetermined`、`not-applicable` | 固定した対象と条件に限った充足判定 |

条件を偶然満たす成果物でも、知識を使った証拠があるとは限りません。逆に、適用記録があっても結果が条件に違反する場合があります。`recorded` は記録の充足を表し、AIの内的な理解や、変更の因果関係を証明しません。

入力不足・未対応の検査・古い根拠を、合格や適用対象外へ変換しません。契約を採用していないことも、適用対象外の根拠にはなりません。

## 説明例

[通常文字のコントラスト契約](definitions/web-normal-text-contrast.json)は、[色コントラストの本文](../knowledge/color-contrast/KNOWLEDGE.md)を根拠とする限定的な数値検査です。Webの文字という適用対象と、この例が扱う通常文字・不透明な一様背景という検査範囲を分けています。大きな文字は、この契約では検査範囲外です。文字コントラストの知識が不要になるわけではありません。

[グループ見出しの契約](definitions/group-heading-purpose.json)は、[グルーピングの本文](../knowledge/grouping/KNOWLEDGE.md)から、既にある見出しが主題や目的を説明するかを取り出した例です。内容、利用者の作業、見出しを照合する意味判断を残します。見出しの存在、文字列の類似度、要素間の距離を代わりの合格条件にはしません。

[製品の判断台帳の例](examples/product-design.record.json)は、デザインシステムがない段階の、製品の担当範囲・結果の意味・状態の伝達・他の接点への引継ぎを扱います。未契約・未決定と、計画したが実施していない確認を残しています。

数値条件と意味判断の原典は、それぞれ [WCAG 2.2 §1.4.3](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#contrast-minimum) と [§2.4.6](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#headings-and-labels) です。原典からの限定と、Mimicが追加した検査範囲・証拠の扱いは、契約の `assumptions` と `limitations` で区別します。

[例の入力と期待結果](examples/README.md)は構造を説明する架空データです。契約の状態は `example` であり、実案件の採用済み基準ではありません。

## 提供範囲

現在提供するのは、製品の設計判断台帳、適用契約の構造と判定規則、JSON Schema、台帳・契約・評価記録の例です。スキーマはJSONの構造を検査します。参照・範囲・証拠の意味は[台帳の境界](product-design.md#意味検査と形式化の境界)、式の評価と再計算は[契約の意味検査](model.md#意味検査の境界)に定めています。

評価器、文書生成器、形式手法への変換器、自動的な契約採用は実装していません。AIは利用手順に従って判断できますが、その報告をプログラムで再検証済みとは扱いません。新しいファイルはPagesの公開一覧に追加していません。Git管理したファイルはRepository上で参照できます。
