# AIが適用契約を使う

製品全体のUI/UXに関する判断を記録し、必要な知識・契約・確認を選ぶときに使います。知識を読むだけで検査を実行する指示にはなりません。Repositoryを変更する場合の作業指示は [guideline/ai.md](../guideline/ai.md) です。

## 製品の目的から判断対象を見つける

1. [設計判断台帳のモデル](product-design.md)に従い、目的、関わる人、利用状況、境界、制約、列挙の根拠と未知の範囲を確認します。目的自体が未確定なら、その判断も登録します。
2. 案件に必要な対象・関係・論点を見つけ、`subjects`・`relations`・`decisions` に記録します。実装済みの画面や、用意済みの契約だけから対象を作りません。提示された例を、追加対象の指定や完全な分類に置き換えません。
3. 各判断を目的・対象・文脈と結び、必要な知識・制約・調査・共通方針を選びます。デザインシステムは、存在し適用する場合の資料の一つです。存在しない段階でも、製品の役割、情報の意味、操作などの判断を続けられます。
4. 候補と採否の理由、未決定、既存の制約との競合、他の判断への依存、成果物への対応を残します。知識の採否と、その契約が適用対象かの判定を混同しません。
5. 判断に合う確認を選び、契約があれば評価記録を参照します。契約がない判断は `unmapped`、判断できない場合は `undetermined` とし、観察やレビューの計画も記録できます。未契約の判断を落としません。
6. 対象範囲と、判断間・利用前後・受け渡しの整合を見直します。未確認や除外の根拠を残し、構造検査や個別契約の合格から全UI/UXの網羅・妥当性を推定しません。

台帳は[専用スキーマ](schemas/product-design.schema.json)に従います。確認計画の `records` が空なら実施記録はありません。実施記録があっても、その結果を読む前に成功と扱いません。知識を適用して確かめる部分では、以下の手順へ進みます。

対象の探索では、利用者の成果までの行為と接点、前提・入力・応答・結果、条件の変化と受け渡しをたどります。要求・調査・仕様・実物を照合し、対応しないものや矛盾を判断・未知として残します。知識の索引と関係グラフから必要な本文を読み、見つかった関係に応じて対象を更新します。これらの問いを埋めたことだけで網羅済みとはしません。

## 契約と根拠を選ぶ

1. [知識の入口](../knowledge/README.md)から必要な本文と出典・補足を読み、対象範囲と版を確認します。
2. `definitions/*.json` の `sources[].concept` と `claim` から契約を探します。知識を参照したことと、契約を採用したことを区別します。
3. 契約の `sources` と `dependencies` の指紋を照合し、根拠の見出しと文脈を読みます。引用の存在だけで契約の解釈を正しいと判断しません。
4. `status` と案件側の採用記録を確かめます。採用前の実案件は `mode: screening` で適用可能性と検査範囲を確認できます。`example` は実案件の採用済み基準にしません。契約がない、採用が未定、古い契約しかない場合は、その状態を記録します。

`mode: evaluation` では、案件の採用権限者と判断記録が必要です。AIが採用を許可されている場合はその権限と根拠を記録します。契約ファイルに `adopted` とあるだけで、人や組織の権限を推定しません。`screening` で適用対象と分かっても、採用済みや充足済みとは報告しません。

## 成果物と証拠を対応付ける

1. 成果物のスナップショットと指紋、対象要素、テーマ・状態・言語などの条件を固定します。
2. 対象集合とその列挙の根拠、未確認範囲を `binding.coverage` に記録します。今回選んだ一要素から全画面の対象集合を推測しません。
3. 宣言された入力ごとに、観測値と証拠IDを対応付けます。値を取得できなければ観測を省き、未確定の理由を残します。実際に観測した空文字はそのまま記録します。未知値を `false` や空文字へ置き換えません。
4. 意味判断では問いと判断基準に照らし、内容・利用者の作業・理由・反例を確認します。提案と承認済み判断を区別します。
5. 要件を設計判断や変更に使った場合は、要件ID、判断対象、行った判断、理由、その証拠を `application_trace` に残します。後から結果を見て適用したと推定しません。

実案件の記録は `output/contracts/<run-id>/` に置きます。[評価記録スキーマ](schemas/assessment.schema.json)に従い、契約JSONへ実測値や結果を書き込みません。外部操作の許可はRepositoryの方針に従います。

## 判定して報告する

[モデルの判定規則](model.md#判定の規則)を使います。適用可能性、検査範囲、適用記録、充足を別々に答えます。不正入力・古い根拠は、違反や適用対象外とは区別します。

未対応演算、型の不一致、対象の不一致は評価できない理由として返します。正常な評価でも、必要な入力がなければ未確定です。確定した反例があれば、他の要件の不足で隠しません。未確認の前提に依存する反例候補は、その条件を付けて報告します。

報告には次を含めます。

- 契約ID・版と、本文・成果物のどの版を対象にしたか。
- 対象・条件・対象集合と未確認範囲。
- 適用可能性、検査範囲、適用記録、充足の各状態と根拠。
- 要件ごとの結果、使用した証拠、不足する証拠、次に必要な確認。
- 数値評価、意味判断、形式証明の区別と、確認できた主張の範囲。

現在は評価器が未実装です。スキーマ適合は構造の確認であり、意味検査や証拠の再計算の完了とは報告しません。AI自身が行った読解・照合と、実際にプログラムで確認した内容を明示します。

## 形式化へ渡す

型・単位・対象集合・前提が確定した `predicate` 要件だけを候補にします。`judgment` は外部判断として残します。承認された意味判断を証明の仮定に使う場合は、その仮定と承認の範囲を明記します。

式へ変換できない要件も一覧に残します。未変換の要件があるのに契約全体を証明済みとしません。単一の契約の合格を、知識全体・画面全体・全利用者への有効性に拡張しません。
