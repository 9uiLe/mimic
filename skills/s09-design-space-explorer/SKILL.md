# S09 Design Space Explorer

## Invocation boundary

The Orchestrator supplies an exact Problem Profile and Product UI Contract, accessible reference source, intent, Run ID, scope, verified locks, assumptions, and authority. Never resolve a floating library revision or silently change a lock. Missing required input or inaccessible source blocks the affected task. Optional domain and journey gaps narrow transfer claims. Do not invoke another Skill or write canonical state.

## Retrieve and explain

1. Traverse each profile trait to a reasoned principle, reference space, case, and mechanism. The local graph representation and retrieval API in `packages/core/src/design-knowledge` is a pure source reader, not a new artifact or an approved shared library. Validate node IDs, edge kinds, rationales, and evidence; dangling references fail. A case cannot lead directly to UI.
2. Assess structural fit independently from context distance. Near needs high fit/low distance; Adjacent needs useful fit/medium distance; Far needs high fit/high distance; Wildcard needs an unconventional candidate and at least medium fit; Anti-reference records a plausible connected trap with low fit. Give reasons and evidence for both judgments. Visual resemblance and novelty alone are insufficient.
3. Use graph retrieval to assemble a deterministic portfolio across principles and distinct mechanisms. History of explicit rejection excludes a case; usage history and maturity inform ordering. Do not fill role quotas. Report uncovered principles, missing roles, rejected or duplicate-assessed candidates, and eligible candidates omitted by a portfolio limit with exact reasons and graph-linked evidence. If no defensible candidate remains, return blocked with zero outputs because `reference-selection.references` requires at least one item.
4. For every selected case, keep the path, structural rationale, context distance, mechanism, maturity, evidence, do-not-borrow details, risks, failure modes, and patterns in narrow provenance or a linked evidence file. Distinguish documented case properties from transfer inference. Preserve rejection reasoning even for nonselected cases. Emit schema-valid `reference-selection` content with `summary` and `references` only; use exact artifact dependencies and pending approval. A case is evidence about a mechanism, never a UI direction.

Before returning, check that each exact `/content` path occurs at most once in each artifact's `provenance` array. A reference item can combine several supporting inputs in one entry. When a reference mixes sourced properties and untested transfer hypotheses, use narrower child-field pointers where possible; otherwise choose one conservative kind and explain the limits in its rationale or `work.unknowns`. Never add separate `derived` and `hypothesis` entries for the same `/content/references/N` path, or a second entry at `/content/summary` for an unknown.

## Limits

Exploration can be provisional, but choosing a durable direction is a later Human Design Decision. Do not invent case observations, empirical validation, shared-library approval, or a numeric quality score. A deterministic portfolio establishes traceability and ordering, not model judgment or research quality.
