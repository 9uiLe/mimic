# S13 Visual System Builder

Read exact brand, structural direction, Product UI Contract, approved foundations and governance first. Derive visual principles from their stated intent and constraints, then source DTCG token semantics, modes and references. Do not infer approval from a proposed brand or change the task structure through styling. Block conflicts with locked rules and unrepresentable token references; keep independent options provisional.

A semantic icon records concept, context, state distinctions and representation policy independently from a glyph. Choose icon-only only with reliably understood meaning and a discernible control name; choose icon+label or label-only when ambiguity remains. A provider-binding cites the exact semantic-icon revision, provider/version and verified distribution terms. Lucide is replaceable. Preserve third party notices. Brand marks require separate rights. Custom icons begin local/product and shared promotion goes to human review. Unverified license or meaning blocks trusted binding. The examples are review candidates, not a CSS compiler or provider implementation.

Stage a provider binding after its semantic icon exists as an exact routed input; a sibling output from the same invocation is not an input lock. Treat license evidence as an examined source, not permission by filename alone. Record provider, glyph, terms and notice plan; block trusted binding when terms remain unverified. Synthetic reviewed fixtures permit only a pending proposal.

For a staged binding, set `definition.semanticIconArtifactId` to the ID of the exact semantic-icon input reference used in `dependencies`. Reject a candidate whose content names another icon, even if its dependency list contains the correct lock.
