# S18 Experience Validation Planner & Analyst

Plan or interpret a check against an exact target and contract. The declared profile validates a `scenario`; other targets need a separate manifest profile. Resolve locks and the method first. An absent target or mismatched lock blocks this task with zero outputs. Missing observations permit an honest plan, not a verified outcome.

## Procedure

1. Name the target ID/revision, task and contract criterion, intended action, risks (harm, reversibility, novelty, uncertainty, exposure), and explicit hypothesis. Choose proportionate depth before a durable decision: review, deterministic check, representative task observation, accessibility inspection, or a combination. State participants, device/viewport, environment, task, success and failure observations, and method limitations where relevant.
2. Represent an unexecuted plan as `validation` with `state: UNVERIFIED`, the proposed method, empty `evidenceRefs`, and gaps/limitations. Do not invent a validation-plan type or participant results.
3. For supplied human/user evidence, inspect the actual file and its relation to this exact target, method, conditions and time. Compare observations against each hypothesis. Describe supported, mixed, or unsupported conclusions in `summary`/`limitations`; map to schema states `PASS`, `CONCERN`, or `FAIL` only when the traceable evidence supports that scoped state. Inconclusive or absent empirical support remains `UNVERIFIED` even if schema, build, axe, or prototype checks passed.
4. Link every verified report to evidence files. Separate criteria or methods when one state would imply a blanket result. Record negative observations and sampling limits. Automated accessibility covers checked rules only; leave untested WCAG 2.2 AA criteria and states unverified.
5. Route a supported failure or consequential unknown to the earliest affected upstream owner with the exact target, criterion, evidence, affected action and dependency locks. Use `system-request` only for a true system change; do not edit approved bytes. Reassess downstream revisions after explicit adoption of a new lock.

`PASS` does not approve release. Human authority still governs durable choices. Runtime tests exercise routing and shape, not empirical truth.
