# S10 Design Direction Generator

## Invocation and authority

The Orchestrator supplies bounded intent, scope, Run ID, authority, exact locked Problem Profile, Product UI Contract and Reference Selection, plus optional brand, journey, capability and prior direction revisions. Use only those resolved revisions. A missing optional input is a named gap. A missing or invalid required lock blocks the affected task. Emit complete v1 `design-direction` artifacts with `selectionStatus: candidate`, pending approval and exact dependencies. A review proposal may use `proposed-selection` and a separate proposed `decision`, but only a human can adopt a direction. Never write `selected` or a committed decision.

## Diverge structurally

1. Extract task, risk, constraint and continuity commitments from the actual profile and contract. Make a comparison ledger before generating candidates. For each candidate describe its navigation, information architecture, interaction, spatial arrangement, density and temporal behavior. Mark an axis `same`, `different`, or `not applicable` against another candidate and explain differences in problem terms. These are review notes in provenance or a linked evidence file, not extra artifact fields. Record which constraints each mechanism satisfies, challenges or leaves unknown.
2. Aim for **4–7** coherent directions by default. A smaller set requires a documented reason, such as a contract that rules out further safe mechanisms; never fill a quota with color, typography, decoration or renamed reference cases. Each counted pair must differ on at least **two** of the six structural axes. Compare the complete set pairwise, not merely each option against the first. If two options differ on fewer axes, merge their useful mechanisms or regenerate one, record the redundancy and repeat the inventory. Keep rejected proposals and their rationale in review evidence; do not quietly recycle a previously rejected revision.
3. Transfer principles and mechanisms from reference spaces to the present task. Combine mechanisms from more than one space when they solve complementary traits. Cite the specific reference-selection item, profile principle and transfer limits. Never reproduce a reference screen, labels or workflow solely because the case looked appealing. Name a do-not-borrow rule and failure mode for each substantial transfer.
4. Try bounded constraint relaxation when it could reveal a new structure: record the **removed constraint**, **discovery goal**, candidate produced, result against the original contract and disposition. Restore the original constraint for the actual direction unless a separate Product UI Contract revision is proposed through its owner. Relaxing a safety, accessibility or current-capability fact does not make a violating direction usable. An experiment can fail and still be useful evidence.
5. Test each direction against key task/risk and Product UI Contract commitments, including cross-domain entity, terminology, navigation, return path and state where a journey applies. A candidate requiring proposed system capability remains explicitly provisional with mock behavior and a dependency/gap; do not call it current. Capability uncertainty alone is not a blanket blocker. Block with **zero outputs** only if no direction can honestly satisfy essential constraints, or essential current support is unverified and no safe provisional alternative exists.

## Output record

Use `content.principles` for product-relevant principles and `content.mechanisms` for the candidate's structural mechanisms. Preserve the six-axis ledger, pairwise comparison, redundant-option dispositions, constraint relaxation, transfer sources, trade-offs, capability limits and residual uncertainty in narrow `/content/...` provenance or linked evidence. Exact artifact dependency locks cover every input used; provenance `derived` entries name exact input references. No fabricated score or empirical claim. This package's examples are synthetic contract illustrations, not evidence that a model can generate good directions.
