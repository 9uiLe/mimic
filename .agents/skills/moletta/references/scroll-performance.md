# スクロールの滑らかさを検証する

主担当 AI が、再現操作・計測・結果の適用範囲を一つの実験として扱う。利用者へ内部コマンドの手配を求めない。実機でしか確認できない体感は人の担当とし、機械で取った性能値と区別する。

## 成果と指標

「対象一覧を同じ初期状態から同じ入力でスクロールしたとき、表示の遅延が許容範囲にある」を成果として具体化する。CPU 使用率、操作の経過時間、平均 FPS だけで滑らかさを判定しない。

[Apple の animation hitch の説明](https://developer.apple.com/videos/play/wwdc2020/10077/) は、表示が予定より遅れた時間と、それを測定区間の時間で割る hitch time ratio を区別している。`ms/s`、割合、フレーム数は別の指標・単位として保持する。分母が計測全体か、スクロール／アニメーション区間かも collector とシナリオに明記し、混在させない。イベント数だけで区間の長さや影響を判断しない。

## 主担当がつなぐ手順

| 段階 | 行うこと | 次へ進む根拠 |
| --- | --- | --- |
| 条件を決める | 対象画面、試験データ、初期位置、操作方向・速度・回数、cold / warm、build・OS・画面設定を決める | 毎回同じ内容を通る操作と、リセット方法がある |
| 操作を確認する | 案件の UI テスト等で到達とスクロールを実行し、対象要素・位置の変化を確認する | 計測を起動できるだけでなく、測りたい操作が起きている |
| 計測能力を確認する | 選択した SDK・OS・端末で利用できる指標と、その出力を短い試行で確かめる | 対象区間・必要指標・単位・試行値が実際に得られる |
| 繰り返しを測る | 性能試験用の設定とデータを使い、測定外で毎回初期状態へ戻す | 反復ごとに別の内容をスクロールしていない。失敗・欠測も記録する |
| 数値を集約する | [対応する構造化出力](performance.md) を選び、元の試行単位を保って取り込む | 同じ collector・端末・区間・条件の baseline / candidate が揃う |
| 必要な原因を調べる | Instruments で対象区間と処理・描画の関連を見る | 時間的な重なりを原因の断定にせず、変更と再測定で仮説を検証する |

比較する両版には、仮想端末なら同じ lease の端末、実機なら同じ許可済み端末を使う。実機を Moletta が割り当てるわけではない。別 worktree が別の端末を持つことと、比較試験の端末条件を揃えることを混同しない。Simulator の値はその環境内の結果とし、実機の性能・体感へ一般化しない。実機の測定も温度・電源状態等の条件を残す。

## XCTest で継続して比較する

スクロール区間の候補は [XCTOSSignpostMetric.scrollingAndDecelerationMetric](https://developer.apple.com/documentation/xctest/xctossignpostmetric/scrollinganddecelerationmetric)。[XCTHitchMetric](https://developer.apple.com/documentation/xctest/xcthitchmetric) を使う場合も、対象 SDK・OS の availability と対象アプリを指定する初期化方法を確認する。API の存在だけで、その画面の必要な指標が返るとは判断しない。

案件の UI テストに指標と再現操作を設定し、性能試験専用の scheme で実行する。測定へ影響する debugger・coverage・診断・スクリーンショット収集の設定を確認し、必要な変更を性能試験の構成だけに適用する。通常の開発・セキュリティ設定を一括変更しない。測定を停止してから状態を戻すなど、リセットや待機を測定区間へ混ぜない方法を選ぶ。

得られた `.xcresult` は `xcresulttool get test-results metrics` で数値を出し、`xcresult-metrics-json` として集約できる。Moletta はテストを生成・起動する専用 runner を持たず、対応形状の出力を集約する。実際のスクロール試験から必要な指標が得られることは案件ごとに確認する。

## Instruments / xctrace で原因を調べる

`xctrace` の記録と `.trace` の解析はホスト・案件側の道具で行う。Moletta の補助 CLI に `.trace` の直接 importer はない。

1. ホストの `xctrace version`、`list templates`、`help record / export` を確認する。Animation Hitches など、必要な観測を提供する template を実際の端末で選ぶ。Time Profiler は CPU 上の原因を調べる補助であり、カクつきの測定値の代用にしない。
2. 許可された端末 ID、対象 PID、時間上限、新しい出力先を明示する。対象省略、`--all-processes`、既存 trace への追記、`--no-prompt` による確認回避を既定にしない。
3. 記録の開始が確認できてから再現操作を行い、終了・trace の確定を待つ。出力パスができたことや終了コード 0 だけで計測完了としない。
4. `export --toc` で run と利用できる table を確認する。実際の schema に合わせ、対象 run・process・操作区間と必要列だけを取り出す。万能な XPath や table 名を推測して固定しない。
5. 必要指標、単位、操作区間、対象への帰属を検査する。任意の XML や trace を AI に丸ごと渡して数値を補完させない。対応する正規化方法がなければ、集約への接続は未対応として残す。

記録には対象以外のシステム情報・パス・識別子等を含み得る。原 trace は必要性と保存範囲を確認したローカル領域へ置き、モデル入力や外部共有へ自動で渡さない。端末 lease を解放しても trace は消えないため、原 trace の保持・削除を別に管理する。[情報の境界](security.md) に従う。

## 完了と未確認を分ける

- 操作未実行、必要 table 不在、対象や区間が不明、記録中断、空出力は未確認。カクつきゼロとして集約しない。
- 明示した計測で得られた数値の `0` と、欠測を区別する。比率の分母が 0・不明なら算出しない。
- フレームを全試行で混ぜたり、各試行の percentile を再び平均して全体の percentile と呼んだりしない。
- 合否は事前の基準、試行数、変動、未確認の範囲を含めて判断する。記録・変換の成功と、性能改善・原因の特定・体感の良さは別の主張である。

この手順は技能が守る判断方針であり、xctrace の記録・解析や実アプリの滑らかさを検証済みという意味ではない。Android のカクつき計測も独立した対応範囲とし、iOS の成功から推定しない。
