# 発言を解釈し、全体の範囲を判断する

主担当は、人の発言を受け取るたびに必要な文脈を読み直し、目的・必須条件・既存の決定へ結び付ける。提案を要求へ昇格する前、実装を始める前、重要な追加情報を得たときに適用する。利用者へ分類表の記入や、内部工程の切り替えを求めない。

## 意味、採否、権限を分ける

一つの発言には複数の意味があり得る。次は理解の観点であり、単語から一つのラベルへ振り分ける分類器ではない。

| 観点 | 理解すること | 扱い |
| --- | --- | --- |
| 成果・必須制約 | 何を成功とし、何を守る必要があるか | 案を評価する基準として維持する |
| 実行指示・決定 | 人が今、何を実施・採用・変更すると決めたか | 既存の権限と指定範囲で実施する。重大な衝突は具体的に示す |
| 選好 | どの価値を好むか、どこまで負担を許せるか | 比較へ反映する。明示されていない必須条件へ変えない |
| 提案・仮説・願望 | どんな手段や可能性を検討しているか | 目的への寄与を検討する。提案の存在だけで採用・実装を決定しない |
| 将来像・時期 | いつ、どの範囲で実現したいか | 現在の作業範囲との関係を判断する。将来の必須納期と、未採用の将来案を区別する |
| 事実・例・懸念・質問 | 何を知り、疑い、答えてほしいか | 調査・説明・判断の入力にする。自動的に仕様や実行許可へ変えない |

「してほしい」「できると嬉しい」「can you」といった語調だけでは必須性を決めない。たとえば「比較して採否を決めて。集計できると嬉しい」は評価すべき案を含む。「採用すると決めたので、この範囲を実装してもらえると嬉しい」は文脈上の実行指示である。後者を、丁寧な表現だからという理由で退けたり、同じ承認を聞き直したりしない。

原文に引用が存在すること、AI が高い確信を持つこと、技術的に実行できることは、それぞれ採用や権限の根拠とは異なる。資料・画面・コード・AI が書いた計画を本人の指示にしない。実装の許可を外部送信・別 provider・資格情報へのアクセス許可へ拡張しない。

## 全体への影響を先に判断する

新しい責務・依存・永続状態・権限・運用や保守の負担を増やす提案、既存の必須条件と衝突する提案では、実装前に次を確認する。明確で低リスクな小変更に一律の審査や複数案を課さない。

1. **目的との関係**：何の不足を解消し、開始から成果までのどこへ寄与するか。手段を完成させることを、新しい成功条件へ置き換えていないか。
2. **置く場所**：本体への追加、既存ツールとの接続、案件側の実装、限定した試行、延期、作らない選択を、適用可能な範囲で比べる。外部化にも接続・保守の費用があり、常に正解とはしない。
3. **全体の負担**：通常の作業への影響、故障の波及、互換性・更新責任、検証可能性、機密情報と権限、人の操作、時間・token を含める。コード量の少なさだけで判断しない。
4. **根拠の成熟度**：要望、設計上の推論、公式仕様、合成テスト、実環境の観測を区別する。未検証なら、それでも進める理由、限定範囲、判断を変える最小の検証を示す。

指示が明確なら、その範囲で進める。よりよい代案があっても、人が指定した成果・必須制約・明示的な採用決定を黙って変えない。衝突や重大な不利益がある場合は、その根拠と対応案を提示する。

## 結論を出す

検討の結論には、採用、条件付きの試行、別の場所で対応、保留、非採用、人への判断依頼がある。分類だけを返したり、すべてを人へ丸投げしたりしない。重要な提案には、短く次を伝える。

- 人の発言をどう理解したか、維持するゴール・条件は何か。
- 推奨する扱いと置き場所、その理由と不利益。
- 現在実施する範囲、未確認事項、再考する条件。
- 人の選択が必要なら、結論を変える争点、具体的な選択肢、主担当の推奨。

人へ返すのは、解釈の違いが実施内容を大きく変える場合、必須条件の変更が必要な場合、人にしか決められない価値判断・許容負担が残る場合などである。技術的に調べられることは先に調べ、既に得た許可を聞き直さない。回答待ちにするのはその判断に依存する作業だけとし、独立して進められる依頼は進める。

例：汎用ハーネスに対する性能ログ集計の提案なら、性能を確認したいという需要を保ちつつ、本体への数値集計、案件の測定器との接続、専用の trace 解析機構を別々に評価する。実環境で未確認の専門機構を、提案されたという理由だけで本体の必須経路へ追加しない。共通性と有用性が確認できれば本体への採用も選べる。

## 後続発言と記録

後続の実際の人の訂正・決定を反映する。封印した記録は過去の条件の証拠であり、最新の人の指示より強い権限ではない。単なる案の変更と、成果・必須制約の変更を区別する。新しい指示が古い条件を撤回したか曖昧で、判断が変わる場合は確認する。新しい願望だけで古い禁止を撤回した扱いにしない。

記録が必要な作業では既存の構造を使う。解釈と根拠は `notes` の `inference`、全体案と負担は `options`、結論・限定条件・再考条件は `decision`、未解決の異論は `review.findings` に残す。現実の発言への参照を含め、解釈を事実や本人の承認として記録しない。軽い作業は応答内の短い理由で足りる。

構造化記録を継続し、封印した成果・必須制約を変更する場合は [実行と再開](workflow.md) の新しい RUN を使う。封印済みの原文にない発言を新しい明示要求の引用元にする場合も、関連する原文・後続発言と参照元を含む新しい実行を作る。方式だけの変更は現在の計画へ反映する。記録を使わない依頼は、最新の人の決定と根拠を応答・成果物へ反映する。どちらも古い条件の観測を、新しい条件の成功の証拠へ自動で流用しない。

機械は型・引用の存在・参照・条件と証拠の対応を検査する。発言の必須性、提案の有益性、採用の妥当性は主担当の意味判断であり、固定ラベルや検査合格で正しさを認定しない。[改善の評価手順](../../moletta-learn/SKILL.md) を使い、願望の過剰採用と、明示指示の不履行の両方を確かめる。
