# 委譲と原文レビュー

委譲は、独立した調査、反証、実物確認が判断の質や所要時間を改善するときに使う。ホストが提供する独立した文脈の実行者を利用できれば使い、特定の製品・モデル・外部 API は必須にしない。主担当が統合と最終判断を引き受ける。

## 作業の委譲

モデル・推論設定を選ぶ場合は [許可した範囲でのモデル選択](adaptive-delegation.md) に従い、実際の利用者の許可とホストの能力を確認する。定型検査は機械で処理し、独立した作業だけへ小さい入力を渡す。調査・実装と、意味上の採否・完了判断の担当を分け、主担当が統合する。

一つの問い、原文と守る制約、参照できる生の資料、書き込み範囲、予算、返す証拠を渡す。共有ファイルの編集担当を分ける。調査結論には実際に読んだ出典、実測には実物への locator と条件、推論には不確実性を返してもらう。

多数意見や人数を証拠の代用にしない。主担当は結果を原文と照合し、矛盾・環境差・省略条件を解決する。案の寄せ集めで全体が成立するとは限らない。

## 原文からの独立レビュー

重要な採用・完了判断、能力の抜けが疑われる場合に用いる。狭い低リスク作業では追加しなくてよい。独立性は文脈の分離であり、異なるモデル名や複数票だけでは確保できない。

1. 最初に原文と最低限の生の資料を渡す。主担当の要約、要求一覧、好む案、疑っている抜け、期待回答はまだ渡さない。
2. 原文から成果・必須制約・成功に必要な能力を再構成してもらう。その後、要求一覧・候補・証拠・成果物を渡して照合し、欠落、成立しない仕組み、根拠を越えた主張を指摘してもらう。
3. 重大度と根拠を付けて返してもらい、主担当が実際に確認する。原文を読んだか、実施方式、指摘、処置と理由を残す。構造化記録を使う場合は `review`、それ以外は依頼された成果物や応答に必要な範囲を記す。レビューのためだけに記録一式を作らない。

`independent_context` は独立文脈で実施した場合だけ使う。同じ会話での読み直しや、独立実行が利用できない場合は `self_review` とし、同じ観点で原文から確認する。未実施は `pending`。独立レビューでも原文の全意味を取り切る保証はない。

`accepted` は指摘の解決まで行った状態で、理由に対処内容を書く。`rejected` には反証、`deferred` には未解決の条件を書く。critical / material を未解決のまま達成扱いにしない。記録を整えるための形式的な却下をしない。

## 技能の行動評価

評価実行者には公開ケース、対象技能、必要な生の資料だけを渡す。採点基準、想定する失敗、候補修正の狙い、過去の結論は渡さない。生成物は隔離した場所に作る。別の評価者が実行後に基準版と候補版を採点し、未使用ケースでも比較する。

実行者が独立文脈で動かなかった場合や、期待する欠落を知っていた場合は、その評価を独立した行動検証と報告しない。詳細は [moletta-learn](../../moletta-learn/SKILL.md) を参照する。
