# Moletta Learn

目的、実行記録、成果物から、観測された失敗と原因仮説を分ける。単発事例から全作業共通の規則を追加しない。何を変え、行動改善・転用・同等品質での負担削減のどれを確かめるかを限定する。

1. 満たせなかった能力と判断箇所を特定する。実装、知識、指示、評価の不備を区別する。
2. 適用条件を限定した改善仮説と最小の候補を作る。回帰ケースには原文と生の資料を用意し、期待回答は評価者の rubric に分ける。
3. 同じモデル・ツール・予算・初期条件で基準版と候補版を実行し、全履歴・成果物・利用量を保存する。独立した評価者が採点し、費用と過剰な手順も比較する。利用量が同じ会話の累積値なら最終値または差分を使い、内数を重ねて足さない。ホストの集計基準が不明なら、その限界を残す。
4. 行動改善・転用を主張する場合は、候補の調整に使っていない新しい非公開ケースで転用を確認する。公開済みの transfer ケースを未見の holdout と扱わない。
5. 重大失敗、ケースごとの悪化、過剰手順を可視化し、修正を狭めるか差し戻す必要を判断する。平均点だけで採用せず、独立した評価、費用、時間、不確実性、人のトレードオフを残す。

`grade` の平均点改善・fresh holdout 等の昇格条件は、行動改善・転用の主張に対するものだ。範囲を限定した保守変更や、品質を保った効率の改善を一律に拒否する条件にはしない。その採否は変更に応じた確認と比較で判断し、ケースの悪化や重大失敗を隠さない。昇格条件を満たさない結果を書き換えず、限定した結果を一般的な改善効果へ広げない。

`docs/evaluation.md` は開発用 checkout の資料であり、導入先ではコピーされない。技能単体で必要な原則はこの文書と [別文脈への委譲](../moletta/references/delegation.md) に含む。評価ツールを使う場合は Moletta checkout の `evaluation/evaluate.py` を実行する。

評価結果は改善候補の根拠であり、共有設定や外部環境を変更する権限を追加しない。技能・実行ツールの構造テストを、判断精度の改善と呼ばない。継続的な利用の失敗を限定した回帰ケースとして育てる。
