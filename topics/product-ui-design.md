# プロダクト全体のUI設計

## この案内について

プロダクト全体のUIを考えるとき、必要な情報、全体の構造、画面と操作、共通の指針、確かめ方を関連付けて読むための案内です。人が判断の理由を学び、AIが設計の際に定義・適用条件・根拠を参照する入口として使えます。

以下の七つはMimicによる読書の整理です。一つの原典が提唱した七段階や、すべての案件に適用する固定工程ではありません。調査や試作で理解が変われば、目的・構造・画面を行き来して考え直します。各概念の定義・背景・対象範囲は、リンク先の本文と出典で確認します。

## 全体を考えるときの立場

- [人間中心設計](../knowledge/human-centered-design/KNOWLEDGE.md)から、利用者の達成したいことと利用状況を理解し、設計を評価しながら更新する立場を読みます。機能への要望と、その背景にある目的を区別します。
- [ユーザージャーニー](../knowledge/user-journeys/KNOWLEDGE.md)から、利用前後の出来事、複数の接点や関係者を含めて体験を見る視点を読みます。画面の外で起きることも、必要な支援に関係します。
- [概念モデル](../knowledge/conceptual-models/KNOWLEDGE.md)から、製品が伝える情報と、利用者が組み立てる仕組みの理解との関係を読みます。設計者の理解がそのまま伝わるとは限りません。
- [デザインシステム](../knowledge/design-systems/KNOWLEDGE.md)から、繰り返す判断を共有し、適用する文脈や変更理由も扱う視点を読みます。一貫性には、言葉、動作、結果の予測可能性も関わります。
- [ユーザビリティテスト](../knowledge/usability-testing/KNOWLEDGE.md)から、設計者の予想と、利用者が課題を試す際の観察を区別して読みます。説明の整合性と、実際に使えることは確認する対象が異なります。

これは関連する立場をつなぐ説明であり、すべての概念が同じ哲学や証拠に基づくという意味ではありません。

## 1. 人と目的を理解する

[人間中心設計](../knowledge/human-centered-design/KNOWLEDGE.md)では、誰が、どのような状況で、何を達成したいのかを扱います。現在の方法、困りごと、利用のきっかけ、頻度、利用上の制約を調べる理由を読みます。利用者本人に加え、支援や運用に関わる人がいる場合も含みます。

ニーズの説明、調査で観察したこと、関係者の意見、まだ確かめていない仮定は、根拠の異なる情報です。「通知機能を付ける」という案からは、その人が何を忘れると困るのか、通知以外の手段があるのかまでは分かりません。

## 2. プロダクトの役割を決める

同じニーズでも、どこまで支援するかは製品やサービスによって異なります。[人間中心設計の対象範囲](../knowledge/human-centered-design/KNOWLEDGE.md)から、利用者の目的と、事業・運用・技術上の制約を関係付けて読みます。[ユーザージャーニー](../knowledge/user-journeys/KNOWLEDGE.md)は、製品が体験のどの部分を担うかを考える手掛かりになります。

この観点で整理する情報には、提供したい価値、対象とする利用場面、支援する範囲、既存の手段との関係、成功を判断する手掛かりがあります。指標が何の達成を表すかも区別します。例えば、記録件数の増加だけでは「必要なときに読み返せるようになった」ことは分かりません。これは本案内の説明用の例です。

優先順位が衝突するときに何を重視するかという原則は、[デザインシステム](../knowledge/design-systems/KNOWLEDGE.md)から読みます。具体的な採否には、その案件の制約と証拠が必要です。

## 3. 情報と仕組みを組み立てる

[情報アーキテクチャ](../knowledge/information-architecture/KNOWLEDGE.md)から、扱う情報や機能、その定義、関係、分類、名前を読みます。内容の量や種類、利用者の言葉、探し方が判断材料になります。情報の関係図、分類表、用語の整理は、こうした構造を表す方法です。

[概念モデル](../knowledge/conceptual-models/KNOWLEDGE.md)は仕組みを理解する枠組みを、[グルーピング](../knowledge/grouping/KNOWLEDGE.md)は意味上の分類と配置から知覚されるまとまりの違いを説明します。情報構造と、画面上でそこへ到達するナビゲーションの関係は、情報アーキテクチャの本文で確認します。

## 4. 利用の流れと状態を考える

[ユーザージャーニー](../knowledge/user-journeys/KNOWLEDGE.md)で、目的が生じてから達成後までの出来事を読み、[インタラクションデザイン](../knowledge/interaction-design/KNOWLEDGE.md)で、利用者の操作とシステムの応答、状態の変化へ進みます。

同じ画面でも、まだ内容がない、入力中、処理中、完了、失敗などで必要な情報と操作は変わります。流れを表す図と状態を表す表は、異なる面を説明できます。中断、戻る、再試行、再開で何が保たれるかも、画面名だけからは判断できません。

これらの関係は、[記録アプリの説明例](../knowledge/interaction-design/examples/recording-app.md)で追えます。作例の状態一覧は、その製品で検討する条件の例であり、全UIに共通する完全な分類ではありません。

## 5. 画面構成へ落とし込む

[情報アーキテクチャ](../knowledge/information-architecture/KNOWLEDGE.md)と[インタラクションデザイン](../knowledge/interaction-design/KNOWLEDGE.md)を関係付けて、各画面が担う役割、現在位置、到達方法、戻り先、操作後の結果を読みます。画面の一覧・階層・遷移図は、情報構造と利用の流れを画面へ結び付ける表現です。試作で構造の不足が分かれば、情報の分け方も見直します。

画面内で何をどう表すかは、[判断材料の選定](decision-material-selection.md)、[視覚的な優先順位](../knowledge/visual-hierarchy/KNOWLEDGE.md)、[レイアウトの余白](../knowledge/layout-spacing/KNOWLEDGE.md)、[Typography](../knowledge/typography/KNOWLEDGE.md)へ進みます。色の判断は[色の知識](color.md)から読みます。それぞれの本文は、全体構造や業務上の優先順位を自動的に決めるものではありません。

## 6. 共通の判断をガイドに残す

[デザインシステム](../knowledge/design-systems/KNOWLEDGE.md)から、原則、文章や用語、パターン、部品、スタイルと、それらを維持する活動の関係を読みます。[Design Token](../knowledge/design-tokens/KNOWLEDGE.md)は、値や設計情報を名前と参照で共有する仕組みを説明します。Tokenの階層や部品数を増やすこと自体で、必要な判断が揃うわけではありません。

ガイドラインに残す内容を考えるため、次の観点を対応付けられます。この表は本案内の整理であり、特定のデザインシステムが要求する共通書式ではありません。

| 残す内容 | 読む際に明らかにすること |
| --- | --- |
| 課題と原則 | 何を解決し、判断が衝突したとき何を重視するか |
| 適用条件と例 | いつ使い、どの状態・内容・環境を想定するか |
| 設計上の理由と根拠 | なぜその判断か、どの調査や既存指針に基づくか |
| 例外と確認範囲 | 何が異なると変更を検討し、何はまだ確かめていないか |
| 維持と更新 | 誰が変更を判断し、どの版が対象か |

実際に共通化する範囲は製品や組織で異なります。既存の指針や部品を調べ、案件で繰り返す判断と不足を把握することと、新しい仕組みを一式作ることは別の判断です。

## 7. 試し、確かめ、更新する

[ユーザビリティテスト](../knowledge/usability-testing/KNOWLEDGE.md)から、確認したい問い、試作品の範囲、参加する人、具体的な課題、観察と解釈の関係を読みます。細部を完成させる前でも、情報の分け方や操作の流れについて調べられることがあります。試作品で再現していない処理や利用環境については、結果を広げて説明できません。

アクセシビリティは、対象者の理解、情報構造、操作と状態、画面表現、確認のそれぞれに関わります。[人間中心設計](../knowledge/human-centered-design/KNOWLEDGE.md)と[インタラクションデザイン](../knowledge/interaction-design/KNOWLEDGE.md)から対象を確認します。入力内容の保護、権限、利用者による中断や修正も、操作と状態を考える際の論点です。

知識本文の出典照合、生成物のリンク検査、AIによる校読、利用者が課題を試す観察は、確認する対象が異なります。どの確認で何が分かったかを保ち、得られた根拠から説明や設計を更新します。

## 例を通して読む

[記録アプリの説明例](../knowledge/interaction-design/examples/recording-app.md)は、「出来事を記録し、後日見つけて読み返す」という一巡を題材にしています。必要情報、対象の関係、画面の役割、操作と状態、共通の指針、確かめたい問いをつなぐための作例です。実製品の要件や、検証済みの推奨設計ではありません。

例を読む際は、ある画面や操作の理由を、利用者の目的と前提までさかのぼって説明できるかを確かめられます。仮定が変われば、構造や流れのどこを考え直すかも対応付けます。

## 出典とこの案内の範囲

各概念の根拠と確認箇所は、本文から参照する `references/sources.md` にあります。GOV.UKのサービス設計、Webの情報設計、Apple製品向けの指針などは、それぞれ対象範囲が異なります。特定組織の必須ルールやWebの適合条件を、そのまま全プロダクトへ適用しません。

七つの章立て、読む順序、概念間のつなぎ方はMimicの編集上の整理です。特定の手順による成果の保証、包括的な事業戦略、法的適合性、個別OSの実装仕様を定めるものではありません。
