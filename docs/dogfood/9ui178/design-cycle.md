# 9UI-178: Mimic による Run モニターの設計検証

## 目的と範囲

保存済み Run を見た人が、異なる設計案を比較し、選ぶ理由を確かめ、次の操作へ進めるようにする。既存 Run、成果物、履歴、サービス URL、別タブの合成プロトタイプを維持する。評価の共通基準は、判断に必要な可視情報、隠れた決定情報、不要なノイズ、次の行動の四つとした。このサイクルではアクセシビリティを設計案の採否基準に含めていない。

## 実 Run と役割

Run ID は `run_mimic_monitor_cycle2_v2_20261009`。保存済み計画はワークスペースの `tasks-9ui178-full-v2.json` で、S04 → S01 → S02 → S05 → S07 → S08 → S09 → S10 → S11 を順に実行した。S09 には 9UI-179 の出典付き playbook を凍結した `inputs/9ui178-reference-sources.md` を evidence として投入した。S10 が作成した全方向の exact refs を、保存後の計画変更をせず `refsFromTask` により S11 へ渡した。実行は既存の Codex サブスクリプション接続による公式モデル呼び出しであり、追加購入や API 課金設定の変更はない。

Mimic の静的 CLI は入力 ref の固定、型、由来、受理状態を検証し、候補が契約に合わない場合は `candidate-rejected` として再試行前に停止した。参照の選択、三つの案、四基準での評価、暫定推奨はモデルの出力である。人間による採用判断はなく、選択の速さ・理解度・満足度も未測定である。受理された S09・S10・S11 の八成果物と digest は [accepted-design-artifacts.json](accepted-design-artifacts.json) に保存した。ここでの `approval.status` はすべて `pending` であり、静的受理を人間の承認とは扱わない。

## 実行で見えた不足と修正

21 回の試行で九つの Task が受理された。S01 の初回試行は旧ロジックが予約前の静的失敗を unknown outcome と誤分類し、明示的再試行を妨げた。S09、S10、S11 のモデル候補には JSON 破損などの静的拒否があり、別途タイムアウトや待機中断もあった。修正後は、モデル呼び出し後でも immutable reservation marker がなく静的検証に失敗した候補を `candidate-rejected` として保持し、明示的再試行で新しい invocation を開始できる。marker がある unknown outcome と混同しない。S10/S11 の出力条件を簡潔にし、上限タイムアウトを 120 秒にした。S10 の三方向から S11 の全方向評価まで到達できた。

既知の完了済み invocation の実行時間合計は約 597 秒で、最初の dispatch から S11 の最終 dispatch まで約 30 分。中断した呼び出しの時間は合計に含めない。この数値は今回の入力・モデル・知識・人間不在の条件による観測であり、後続の手法比較では条件をそろえる必要がある。早い人間判断が設計の収束を助ける可能性はあるが、JSON 破損やタイムアウトの解消は別の課題である。
