# Public seed design knowledge

`knowledge/seed/graph.json` is a local `DesignKnowledgeGraph` input for the read-only helper in `packages/core/src/design-knowledge`. `spaces.json` supplies the human-reviewable Reference Space fields that do not have typed graph-node fields. `sources.json` is the evidence ledger. The three files form one versioned seed corpus; load them together.

Each space records a problem trait, principle, mechanism, documented case, conditional pattern, good and poor fit, failure mode, and superficial features to avoid. The graph follows trait → principle → space → case → mechanism → principle. It never connects a case directly to a UI direction. All nodes are `provisional`; inclusion in this public seed is not approval of a shared knowledge promotion or evidence that the proposed transfer works.

The ledger distinguishes `observation` from `transfer-hypothesis`. An observation is a concise paraphrase of a named section of a primary source. A hypothesis is original analysis about potential use in another problem. Each entry records its own access date. Evidence IDs resolve from graph nodes and edges to this ledger; a source citation alone does not validate transfer. Structural fit, context distance and exploration role must be assessed for a particular problem. No case carries a permanent Near, Far or Anti-reference role.

The corpus contains original summaries and references by URL only. No third-party screenshots, icons, CSS, prose passages, brand assets, or source files are bundled. Brand and product names identify observed cases. The rights strategy for each entry is recorded in the ledger. If later work bundles an upstream asset, apply `THIRD_PARTY_NOTICES.md` and the exact upstream rights before distribution.

Run `pnpm test packages/core/src/skill-catalog-tests/seed-knowledge.test.ts` to check shape, linkage and representative retrieval behavior. Those structural tests cannot establish factual accuracy, source accessibility over time, legal rights for future assets, or product-specific transfer fitness. The initial source and content review is recorded in `knowledge/seed/research-review.md`; the 2026-10-09 product UI additions are in `knowledge/seed/product-ui-source-review.md`.

For S09 tasks involving product direction comparison or Run progress, copy `knowledge/seed/product-ui-playbook.md` into the Run workspace, then pass that workspace-relative copy as an `evidenceFiles` input. The CLI reads contained workspace files into the session prompt; a path in the repository outside that workspace is rejected, and loading the graph in a separate script does not by itself give the agent access to it. Record the copied file's digest in the Run evidence trail. When graph-based retrieval is required, a host preparation step must assess the current problem, call `retrieveDesignReferences` with the graph, and provide a compact source-linked result through another workspace-contained S09 evidence file. S09 cannot call the graph helper just from the playbook text. Without that prepared result, S09 may assess the four described cases but must not claim graph retrieval was run. Its `reference-selection` is then passed as the exact S10 input. Recheck each ledger URL and section, paraphrase, fit boundary and hypothesis before product-specific use.

For a specific screen's information hierarchy, use `knowledge/seed/purpose-information-playbook.md` alongside the current Problem Profile and Product UI Contract. It distinguishes Mimic's Design Package decision task from the local monitor's diagnostic task and asks which decision facts belong in the overview, on demand, or outside the screen. Two additional graph spaces link the first-party GOV.UK Details and multi-task list examples to bounded explanation and multi-session progress. Their observations and Mimic transfer hypotheses are separated in `knowledge/seed/purpose-information-source-review.md` and `sources.json`. Copy the playbook into a Run workspace before listing it in `evidenceFiles`; the graph helper still requires host-side preparation as described above. Evaluate alternatives against one concrete task and record missing decisive information separately from excess noise.
