# Authored prototype journeys

`buildPrototypeJourney(store, plan, outputRoot)` emits one local synthetic specification bundle with several domain views. It uses the existing prototype builder's exact scenario, selected-asset, token, responsive, semantic-tree validation and renderer for each view. Every view resolves its own approved scenario and ancestor-scoped dependencies. The Product journey and common Product UI Contract have exact locks; a Queue scenario does not acquire a Review sibling dependency.

The `PrototypeJourneyInput.version: 1` plan is non-artifact authoring input. Its saved canonical bytes and SHA-256 digest bind the view IDs/routes, per-view render plans and fixture values, Product and domain references, entity data, filter and draft fields, explicit empty-result feedback, every control action, row/text bindings, initial values, and retention rules. Artifact approval does not approve later authored UI intent. Unknown versions, routes, fields, actions, missing controls, bad locks, unsupported types, and out-of-scope source references fail closed. Inputs are copied before asynchronous reads.

Route, semantic UI status, entity/filter/draft data, and presentation focus/disclosure are independent. Supported local actions are `select`, `navigate`, `return`, `set-filter`, `edit-draft`, `discard-draft`, `reset-draft`, and `set-status`. A control binds an authored node ID to one finite action. Entity fields are read-only; only listed draft fields can be edited. Empty draft strings are valid. Filter and entity-keyed drafts stay in memory for the page session until explicit discard; return context remembers the source view and focus target. Reloading resets state. The runtime uses text content and input values, with no arbitrary code, raw HTML, backend calls, or production persistence.

One document `main` contains all views. DOM IDs are namespaced as `viewId__logicalNodeId`, while the saved plan keeps stable logical IDs. Fragment targets, responsive operations, focus maps, and controls use the same mapping. Each view retains its own semantic states; loading/empty/success/error are not domain routes. The 9UI-151 hidden-focus repair and 9UI-143 reorder, collapse, progressive disclosure, replacement, and resize behavior remain active. When navigation or a status change programmatically focuses a destination heading, a user-initiated forward Tab moves to the first visible control in that state. This finite focus handoff preserves the heading as the immediate focus target and makes recovery reachable on macOS WebKit without changing OS settings.

Compiled token definitions must be identical across views. A conflict is rejected rather than letting one domain silently override another's global CSS variables. Per-view layout and style rules are scoped to that view.

The [C-204 fixture](../../fixtures/prototype-journey/README.md) provides a local demo and numbered observations. Its Queue filter and C-204/C-205 draft isolation run on the emitted files, alongside exact static/browser quality gates, HTML lint, axe, keyboard, focus, error recovery, and resize checks. These are synthetic observations only.

## Browser environment finding

The emitted C-204 journey and gate pass in the local Chromium desktop/mobile and WebKit desktop/mobile viewport checks, including the strict Tab/Enter recovery assertion. Before the journey focus handoff, local WebKit failed at the forward Tab after the Review error heading. The separate legacy single-view WebKit focus difference remains tracked in 9UI-146; this journey result does not close that issue. Firefox on this host has a separate sandbox launch limitation. These bounded checks are not a claim about every browser or universal keyboard readiness.
