# S12–S15 design resolution and composition packages

These four static Skill packages implement the reasoning boundaries in [9UI-90](../specifications/reasoning-skill-contracts.md) and the [Design System package](../specifications/design-system-package.md). The Orchestrator supplies exact locked artifacts, scope, intent and authority. The packages neither invoke one another nor mutate approved revisions. Their examples and scenarios are synthetic contract fixtures; they do not establish live AI reasoning quality, user outcomes, license clearance, or accessibility conformance.

- **S12 Design System Resolver** selects unchanged approved assets or proposes a constrained configuration, extension, or genuinely new asset. Fit to task and governance drive the choice; reuse percentage is not a target. The package requires direction, contract, task model and applicable assets. Multiple approved assets, including governance, bind through its `approved-assets` input. It blocks on invalid or stale locks, ambiguous policy, forbidden variation, missing mandatory asset, or unverified provider terms. Rejected candidates require a new revision.
- **S13 Visual System Builder** derives foundation and DTCG token semantics from brand, structural direction, contract and approved foundations/governance. Existing token and icon revisions can bind alongside governance through `foundations-and-governance`. Semantic icon meaning is independent of the replaceable provider glyph. Provider bindings need exact semantic-icon dependencies and verified license terms before trusted use; the example's license is marked for review. This package does not compile CSS or supply a production provider.
- **S14 UI Composition Planner** resolves task → pattern → layout → components against usage, anti-usage, state and accessibility constraints. Existing variants and composition take precedence over new local components. It emits a canonical `scenario` with actor, context, steps and expected outcome. Its selected pattern, layout and component references belong in exact dependencies; composition rationale belongs in narrow provenance or linked evidence. No composition-plan artifact exists in v1. Proposed capabilities remain mock only.
- **S15 Responsive Architect** records justified preserve, reorder, collapse, hide, replace, split and progressive-disclose decisions for viewport, input and content constraints. The mobile primary goal must remain available, including meaningful state and accessible reading order. A reusable responsive or accessibility rule is a proposed `design-system-asset`; changed interaction steps may produce a revised `scenario`. Multiple selected pattern/layout/component and existing responsive assets bind through `selected-assets`. Without observed viewport evidence, empirical parity remains `UNVERIFIED`.

The [bridge tests](../../packages/core/src/skill-catalog-tests/s12-s15.test.ts) load manifests with the shared loader, validate canonical output examples, consume each named scenario field, exercise property policy and revision guards, and route synthetic inputs and outputs through `runSkillPackage` and the Orchestrator. The runtime checks exact references, dependencies and output authority. It cannot determine qualitative task fit, provider rights, or empirical design quality. Blocked work produces no invented artifact. Rejected work is preserved as history and must be proposed as a later revision with pending approval.

## Staged outputs and deterministic fixture checks

The S13 example's provider binding depends on its semantic icon. The Orchestrator rejects returning both as a sibling bundle when the icon lock was not in that invocation's inputs. The bridge first produces the foundation, source tokens and semantic icon, then invokes S13 again with the icon's exact produced reference bound alongside the foundation/governance input. A synthetic provider review fixture is read through the declared evidence-file input: an unverified fixture blocks the binding task, while a reviewed fixture permits only a **proposed** binding. The fixture does not clear an actual third-party license.

The S14 example carries separate pattern, layout and component snapshots. Its scenario locks those revisions and records Task → Pattern → Layout → Components rationale in scenario provenance. The bridge binds three distinct runtime asset references and preserves that rationale in the emitted scenario. Removing the layout lock or using the pattern to rank unverified evidence yields a zero-output blocker with a specific reason. S12 also exercises an unchanged approved organization asset against approved governance, including a tampered canonical lock and forbidden child variation.

S15 routes both the responsive rule and mobile scenario. Its deterministic fixture check compares the source scenario's explicit primary action with the mobile steps before output acceptance. Removing the mobile decision path yields a zero-output blocker. This check establishes traceability for the example's stated action; it cannot assess whether the interaction succeeds with real users or across actual devices.
