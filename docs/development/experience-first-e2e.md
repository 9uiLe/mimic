# Experience-first cross-domain dogfood (9UI-125)

This is a synthetic, inspectable case review exercise. It does not establish a user outcome, a real human design decision, a production release, or WCAG 2.2 AA compliance. The source is [`fixtures/dogfood/experience-first/case.json`](../../fixtures/dogfood/experience-first/case.json); the fixture authority accepts only `decision_fixture` and `human_fixture` in temporary storage.

## Desired experience and canonical path

An operator opens C-204 from a filtered queue, reviews evidence in a separate review domain, returns to the same queue filter, and resumes the case without accidentally approving it. Queue and review differ in primary goal, interaction model, information structure, time behavior, risk, and session model. The journey declares five retained context fields: entity, terminology, navigation, return path, and draft state. The Experience-first Run begins from the desired behavior and an exact reused journey; it proposes a revision of the same Product UI Contract type that System-first uses. The Run API has no mode-specific output schema. This demonstrates canonical type and package-format convergence, not equivalence of two independently executed full projects.

The fixture writes approved snapshots only through `ArtifactStore` with explicit fixture authority. Organization identity, product context, and review-domain context are separate design-system assets with exact dependency locks. `DependencyGraph` verifies their closure. The review scenario locks the Product UI Contract, review domain, journey, selected pattern, layout, component, responsive and accessibility rules, and token source. Its S14-style composition provenance names the selected pattern, layout, and component with exact digests. The queue domain is a sibling; a queue-scoped artifact cannot lock the review-domain artifact. The journey at product scope records the cross-domain relationship without violating ancestry.

`buildPrototype` consumes the approved exact scenario and an **authored, non-artifact** render plan. Its generated HTML/CSS/JS and manifest are verified by static gates and by Playwright in desktop and mobile Chromium. The browser tests inspect visible case identity and return context across loading, success, partial, error, permission, empty, and disabled states, repeated transitions, and actual section positions. On the C-204 success view they also verify the emitted mobile DOM order, focused case-navigation replacement, keyboard-opened evidence and history disclosures, mapped focus and open state across both resize directions, and the primary action. The saved responsive plan binds these operations to the exact selected rule and is included in the bundle digest. Browser gate results remain inspection results. The static gate's UI Contract semantic match is a `CONCERN`; its source identity and approval checks do not prove that the authored text faithfully represents the contract.

The fixture Run submits a candidate with alternatives `adopt` and `retain`, then simulates rejection in temporary storage. It verifies that the rejected revision remains immutable, canonical selection does not move, and a renewed proposal must cite the rejection ID. These simulated records exercise the registry's mechanics. They are not owner decisions.

The package test compiles the same exact selected review artifacts, generated prototype bytes, and static quality report into Reference and Portable **candidates**. A synthetic organization package is an exact external dependency; Portable uses an explicit fixture redistribution grant and bundles its bytes. `PackageRegistry.reconstruct` verifies each candidate with the same schema, scope, lock, approval, and license checks. A publisher with no trusted release decision refuses both candidates. No production directory, provider credential, or network publication is used. The sibling queue-domain artifact is not included in the review-domain package because the registry rejects it as out of scope. The test also compiles Product-scoped Reference and Portable candidates that explicitly inventory both Domain artifacts and the Product journey. Reconstruction verifies their exact locks and original Domain scopes while preserving the organization dependency and Portable redistribution rule. These remain candidates: the publisher refuses them without a trusted release decision. Product inventory does not permit sibling artifact consumption.

## Mobile contract and remaining route limits

The authored responsive v1 plan is saved in `plan.json` and sealed by the manifest's plan digest. Its `success` entry cites the exact approved responsive-rule reference, rationale, stable node IDs, continuity mappings, and four finite operations. `reorder` places the decision before context and secondary evidence in actual DOM order. `collapse` and `progressive-disclose` use native named disclosure controls. `replace` supplies an explicit focused case-navigation subtree and maps its local back-to-overview anchor for focus continuity. The anchor targets the current review view, not the queue domain. The implementation keeps the same state renderer and preserves status, disclosure-open state, and appropriate focus through both resize directions. The approved scenario steps and selected-asset locks are unchanged because the synthetic task sequence has not changed; approval of that scenario is not approval of the separately authored mobile semantics.

A separate reproduction adds an `/review/C-204` link, a `review` state transition, and a draft `<input>` to otherwise valid copies of the plan. The builder still rejects them respectively as a non-fragment URL, unsupported state, and unsupported semantic element. Static text such as “Queue / Review” and the new local anchor do not establish an actual journey or draft persistence. These are tracked by 9UI-148.

The repeated `success → empty/partial → success` browser regression in [9UI-151](https://linear.app/9uile/issue/9UI-151) exercises the generated C-204 view. Before the fix, clicking `#show-empty` left focus on that hidden source button and the following natural Tab missed a visible control. The regression failed against that behavior. The generated renderer now moves focus to the visible destination heading when the previous focus becomes hidden; the heading is programmatically focusable but stays out of sequential Tab order. In Chromium, one natural Tab reaches the visible `Show success` control, and Enter returns to success. The test repeats this route for empty and partial states, uses keyboard activation, and verifies focus and status across resize. Existing replacement anchor and disclosure mappings remain checked. The browser gate separately focuses the body with temporary `tabindex=-1` for its isolated first-Tab probe and removes the attribute after Tab. That probe does not establish the route behavior; the generated browser regression does. On this macOS host, a WebKit Tab from a newly focused destination heading moved focus to the body; keyboard readiness there remains open alongside the separately tracked first-Tab difference in 9UI-146.

The bounded Product Design Package inventory rule is specified in [9UI-144](https://linear.app/9uile/issue/9UI-144) and [the multi-domain package contract](multi-domain-package-contract.md). It permits explicit descendant artifact containment, without changing package or artifact dependency consumption, promotion, or release authority.
