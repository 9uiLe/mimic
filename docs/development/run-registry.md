# Run and Decision Registry

The local barrel `packages/core/src/run-registry/index.ts` exposes the 9UI-99 model without changing the package root export, which is owned by 9UI-116. The registry records exact canonical bases, Run-owned provisional revisions, scoped Decision Packets, immutable human Decision Records, audit events, and canonical selection. It does not call Linear. IDs and URLs for Linear may be recorded as ordinary references by a later adapter; no issue or comment is created by this module.

`RunRegistry` takes a verified `SnapshotReader`, a `RegistryAuthority`, and `TransactionalRegistryStorage`. The reader must check stored schema, provenance, scope, digest, dependency locks, and approval authority; `ArtifactStore` is the existing reader. `RegistryAuthority.verify` checks the human actor and precise decision. `allowCommit` repeats authority and policy checks at the point of effect. These callbacks must use authoritative sources rather than trust the decision payload. Inputs are copied before awaits. A rejected exact revision cannot be proposed again; a renewed revision must cite the previous rejection decision.

`FileRegistryStorage` stores a complete registry state in one JSON file. A writer acquires an exclusive directory lock, reads current state, runs guards, writes and syncs a temporary file, then renames it over the state file and syncs the containing directory. The rename is the single visibility point for canonical selections, proposal fates, decision records, and audit events. A failed guard or write before rename leaves the old state intact. A lock left by a terminated process requires an operator to verify that no writer is active before removal; this implementation never steals it. On a failure after rename, callers must inspect state before retrying. The in-memory transaction used in tests has the same all-or-nothing contract.

A Human Commit Point names exact proposal and decision IDs from one packet. Its transaction rereads current canonical selection and each locked dependency, checks candidate freshness and approval state, rechecks human authority and policy, and updates only the named selections. Unnamed siblings remain pending. If any check fails, none of the set is selected. The registry selection carries the approving decision ID, so consumers must resolve the effective approval through the registry.

## Integration boundary requiring follow-up

`ArtifactStore.create` appends one artifact revision per call and has no atomic batch or shared transaction with canonical selection. This implementation therefore **does not** claim that an approved artifact envelope is atomically published to `ArtifactStore` with a commit. It selects the exact proposed snapshot with a registry-owned approving decision record. Consumers must not treat `ArtifactStore.read` of that proposed snapshot as an approved envelope. To meet the full artifact lifecycle contract across both stores, the owner of the storage API must add a transaction that publishes all approved revisions, approval envelopes, immutable decision records, and canonical selection in one commit, or define a verified registry overlay as the authoritative approved envelope. Sequential `ArtifactStore.create` calls cannot provide that guarantee. Public package exports and downstream Orchestrator integration remain outside 9UI-99's write set.

Run state derives in this order: `review-ready` for any pending proposal, `active` for a safe reversible action, `blocked` for unresolved blockers, and `closed` otherwise. Explicit discard records every proposal's fate and preserves decisions and audit history. A closed branch rejects further mutations. Neither a pending human choice nor an individual blocked work item prevents independent safe exploration.
