# Run and Decision Registry

`@mimic/core` exports `RunRegistry`, `ArtifactStorePublication`, `RegistryAuthorityVerifier`, and `FileWorkspaceStorage`. A Run starts from verified exact approved canonical revisions at a recorded scope and entry mode. It owns provisional revisions and explicit Decision Packets. Immutable human Decision Records bind one proposal to an exact approved or rejected output snapshot. Proposed work and decisions do not change canonical selection by themselves. Decision Packets and Records can carry external references, including Linear URLs, in exported registry snapshots. These APIs perform no live Linear action.

## Atomic publication

Use one `FileWorkspaceStorage` instance for both `ArtifactStore` snapshots and the Run registry. Construct `ArtifactStore` with `workspace.snapshots`, a `RegistryAuthorityVerifier` backed by the workspace, and the applicable seed authority verifier. Pass that store to `RunRegistry`, and pass an `ArtifactStorePublication` made from the same store and registry authority. A standalone `FileRegistryStorage` can record provisional work but refuses commit and rejection publication: it cannot atomically publish artifact envelopes with canonical selection.

A commit request supplies a stable ID and names exact proposal and approved Decision Record IDs from one packet. The decision binds the proposed revision and a complete planned approved artifact revision, including final approval envelope, dependency locks, revision, and digest. The planned output in a Decision Record is approval intent; it is not an approved `ArtifactStore` artifact until the Human Commit Point completes. The registry rechecks the current canonical selection, human authority, policy, candidate freshness, exact locks, and the final effect graph across every named output. It publishes approved output revisions through the normal `ArtifactStore` schema, scope, revision, dependency, provenance, digest, and authority guards, using a transaction-local snapshot view. Only named outputs become canonical. Rejection similarly publishes a new rejected revision and records the decision without changing canonical selection. Prior approved and rejected revisions stay immutable. A renewed candidate in any Run after rejection is a new revision that cites the latest rejection decision for that artifact.

`FileWorkspaceStorage` stores immutable artifact records and registry state in one versioned JSON file. Writers acquire an exclusive directory lock, validate and stage changes in memory, sync a temporary file, rename it over the state file, and sync the directory. The rename is the only visibility point for new revisions, Decision Records, canonical selection, proposal outcomes, freshness assessments, and audit events. Failure before rename leaves all changes invisible. A lost response after directory sync can be resolved by retrying the same commit ID and exact request; a changed request with that ID conflicts. The backend never steals a leftover writer lock; an operator must verify the writer is gone before removing it. It provides atomicity only on a local filesystem with atomic same-directory rename and working `fsync`. There is no automatic migration from an existing `FileSnapshotStorage` tree.

The reader must use the same workspace and `RegistryAuthorityVerifier` so an approved or rejected revision reads back with its verified full envelope. A registry decision alone never turns a proposed snapshot into an approved artifact. The ordinary readback verifier accepts an approved output only when the exact decision and output appear in a completed commit record; the transaction-local publisher can verify staged output before that commit record becomes visible. `ArtifactStore.read` remains the artifact integrity boundary. The older `FileSnapshotStorage` and `ArtifactStore.create` single-revision APIs remain available to existing consumers, but they do not provide a multi-artifact Human Commit Point.

## State and review guards

Run state derives in this order: `review-ready` for an eligible pending proposal, `active` for a safe reversible action, `blocked` for unresolved blockers, then `closed`. A stale or unverifiable pending proposal is recorded with a reason and does not count as review-ready. A deferred human decision holds only its named proposal out of review readiness; safe exploration may continue, and a later explicit human decision can resolve the hold. Superseding a deferred or stale proposal removes only that proposal's old review hold. Resolving another blocker needs verified evidence or an approved human Decision Record explicitly bound to the same Run, blocker ID, current reason, and conclusion, with current authority rechecked. A blocked or closed Run cannot produce or submit. Explicit discard records every proposal's fate; automatic closure records a final fate map. Neither path reopens a closed Run. Ordered events include the Run, canonical selection, and freshness state after each action, allowing Run-state reconstruction without private reasoning.

Exact historical approved dependency locks remain valid when policy and `onChange` permit them; newer revisions never retarget a lock automatically. Approved outputs that explicitly depend on another output in the same commit are published in dependency order and become visible together. The registry records downstream `stale` or `blocked` findings from the exact dependency graph as state events, leaving approved artifact bytes unchanged. `validate` impact handling requires verified evidence, `revise` requires an explicit new output revision, and `invalidate` blocks an unhandled change.

The Orchestrator and release flow remain separate. They must use the registry's verified canonical selection and freshness assessments; a schema pass or a pending decision never grants release authority.
