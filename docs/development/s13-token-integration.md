# S13 token integration

S13's [example token asset](../../skills/s13-visual-system-builder/examples/output.json) is a pending proposal. Its `definition.tokens` uses the CSS-ready subset of the [DTCG 2025.10 token compiler contract](token-compiler.md): top-level `primitive`, `semantic`, and `component` layers, explicit or inherited supported types, typed concrete values, and complete same-type aliases to the same or an earlier layer. The example is not a general DTCG implementation. An unsupported structure, value, mode, or reference must be revised explicitly; approval cannot make invalid bytes compile.

The [dedicated bridge test](../../packages/core/src/skill-catalog-tests/s13-token-integration.test.ts) loads the canonical Skill package and example, seeds exact approved synthetic inputs, and calls `runSkillPackage`. The produced token revision remains proposed and cannot compile. The test then submits that exact candidate to the Run registry, simulates a named human decision and commit through the registry authority, reads back the newly published approved revision from the Artifact Store, and passes its exact revision and digest to `compileApprovedTokenAssets`. It asserts the actual CSS custom properties, aliases, input dependencies, provenance, canonical reference, and compiler source locks. Mutating the caller's reference after compilation cannot relabel the result. Wrong digests, legacy and malformed typed values, unresolved aliases, and rejected history fail closed; retry requires a later candidate revision that cites the rejection.

The test's human identity and authority are deterministic fixtures used to exercise the existing approval and publication guards. They are not evidence that a human reviewed the design, that an AI reasoned well, or that the color choices work for users. A deployment must obtain real human authorization through its configured authority mechanism before compiling an approved revision.
