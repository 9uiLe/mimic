# Design Package compiler and local publication

`packages/core/src/package-compiler` constructs Design Package candidates and publishes them to a trusted local filesystem root. It reuses the package registry's `PackageManifest`, `DesignLock`, document serialization, and `mimic-package-bytes-v1` digest. The registry remains a read-only resolver.

## Candidate contract

Call `compilePackage(input, artifactStore, registry, releasePolicy, registryForSource)` with an exact package ID, version, mode, scope, approval reference, owned file bytes, exact artifact selections, dependencies, quality reports, and an inventory classification for every category. `registryForSource` creates the existing registry with the caller's normal authority, schema, scope, and license policies for an overlay source containing the candidate. After exact release approval, the publisher uses it to reconstruct the candidate before staging and again before commit. The categories are product foundation, experience structure, Design System, interface and system boundary, prototype, scenarios, quality, decisions, and handoff. Classify each owned file, artifact, and direct external dependency in exactly one category. A missing category is rejected. An absent optional category needs a reason. Product foundation, prototype, quality, decisions, and handoff are required for a design release. The prototype must include `index.html`, `prototype.css`, `prototype.js`, `plan.json`, and `manifest.json` under `prototype/`.

A registered Product-scoped Design Package can select approved, fresh snapshots from two or more registered Domain scopes and their Local descendants into its explicit `experience-structure` inventory, together with a Product-scoped cross-domain journey. Journey domain names are semantic content, not dependency locks. Selected artifacts keep their source scopes and exact revisions/digests; this inventory does not change package or artifact dependency consumption. `compilePackage` returns a candidate with `verifyResolution`; the publisher invokes that check after exact release approval before staging and again before commit. Candidate creation alone is not publication. See [the multi-domain contract](multi-domain-package-contract.md).

The compiler copies its inputs before asynchronous reads. It resolves each selected artifact from `ArtifactStore`, checks its exact revision and digest, approved lifecycle and approval, valid freshness, and selected artifact dependency locks. For a new release, consumed external artifact dependencies must also resolve through the trusted `ArtifactStore` at the exact digest with verified approval and valid freshness; an unavailable trusted record blocks the release. Historical or contextual package artifacts outside the selected dependency closure remain readable through the registry. The package contains serialized artifact snapshots and the owned files. `inventory.json` and `quality/evidence.json` record the category account, supplied findings, and per-finding release policy decisions. Findings retain their five states and four severities. A policy decision supplies a reason and says whether that finding blocks release; a blocked result throws `PackageCompilerError` with all decisions attached. Human release authority is a separate check. A policy may permit a disclosed concern but cannot turn it into a pass. Source validation reports have to match the exact five prototype file digests and bundle digest, and name selected artifact revisions. Any prototype byte change invalidates those reports.

Reference mode records exact dependencies as external edges, with acquisition hints. It does not fetch a remote URL. Portable mode requires an explicit trusted caller redistribution grant for each exact transitive dependency and bundles its bytes. The existing registry's portable closure rule means a dependency snapshot with a transitive external edge cannot be used as a portable child; acquire a separately released self-contained version or release a Reference Package. The compiler reports the missing closure or permission and does not label a partial bundle portable.

## Local publication

`FilePackagePublisher.publish(candidate, authority, { signal })` verifies the candidate digest, re-reads the selected artifact revisions, and asks a trusted local authority to verify a release decision bound to the exact package ID, version, mode, manifest, lock, inventory, quality decisions, and final package digest. The callback in tests is a simulation, not evidence of a real human decision. The publisher stages a complete directory on the same filesystem, serializes cooperating writers with an exclusive per-version claim directory, rejects any existing version, and renames the completed stage into place. Cancellation is checked again immediately before the atomic rename; cancellation or failure removes staging and claim directories. The result is readable by `FilePackageSource` and `PackageRegistry.reconstruct`.

This implementation targets a trusted local output root and cooperating local writers. It does not provide hostile OS actor protection, a retention policy, network publication, production credentials, signing keys, or a hosted registry. The caller supplies human authority, license policy through the registry, and redistribution decisions; the compiler cannot infer those from file names or license strings.

Run the focused suite with `pnpm exec vitest run packages/core/src/package-compiler/package-compiler.test.ts`, then the repository's canonical `pnpm check` and browser checks with Node 24.21.0 and pnpm 12.9.1.
