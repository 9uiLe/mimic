The test keeps its 300-second cap, seven states, primary action, both responsive directions, natural keyboard route, 12 exact gate findings, and `UNVERIFIED` negative control.

Its bundle log followed the journey, browser gates, and inspection at about 10:06:40, roughly 24 seconds after suite start at 10:06:15.914. The remaining original awaits were `server.close` and temporary-root `rm`, so that log narrows the stall to cleanup; it does not identify which await stalled. A separate [PR #56 browser run 37607403045](https://github.com/9uiLe/mimic/actions/runs/37607403045), head `da4891b369b1935fb9401b53715def0b93763fa5`, used two workers and passed 51/52 Chromium tests. Its new journey test passed, while the unchanged existing C-204 body failed on Chromium mobile at line 348 after Enter, again expecting desktop `#case-context h2` focus. That branch generated a different bundle (`sha256:aad9f0bc84e117a1cfe198bba35c25e166e2265578cbe321b2aab4c6e6bccbd4`), so this is an independent recurrence of the resize/focus symptom, not an identical-bundle rerun. These runs do not establish a product runtime defect or a particular socket cause.

An unmodified local run on pinned Node 24.21.0/pnpm 12.9.1, Chromium desktop/mobile, two workers, passed 2/2 in 15.4 seconds. A bounded Node 24 localhost probe retained one **active** response on a test-owned server: 111ms after calling `server.close`, its callback had not fired; calling `server.closeAllConnections` after `server.close` made it fire by 112ms. This demonstrates a possible indefinite cleanup wait without attributing the hosted failure to an active response. Node's [HTTP documentation](https://nodejs.org/docs/latest-v24.x/api/http.html#servercloseallconnections) specifies that ordering and says this method closes active HTTP connections. In Node 24, ordinary idle keep-alive connections are already handled by `server.close`; their presence is not the established cause here.

## Observable synchronization and cleanup

The generated responsive runtime listens for `matchMedia` changes and restores the desktop subtree. The empty-state status and heading can already be correct while the hidden success subtree still has mobile structure. With phase instrumentation under two workers, the `order()` read immediately after mobile-to-desktop `setViewportSize` still returned `[review-decision, mobile-case-nav, evidence-list, decision-history]` in three of four C-204 runs. The desktop restoration check then observed `[case-context, review-decision, evidence-list, decision-history]` after 117–120ms in those runs. This is the reported missing-readiness window: an immediate Tab/Enter can activate success before restoration, leaving focus on the then-correct mobile heading. The test now waits for the desktop order, `#case-context` presence, `#mobile-case-nav` absence, and absence of responsive disclosure wrappers before the original empty focus, natural Tab/Enter, and desktop heading assertions. Both reverse resizes wait for the mobile order and replacement before their existing focus checks; the final reverse also checks both disclosure wrappers. No fixed delay or test-side focus action was added.

Named monotonic phase logs include fixture/build/listen, layout and responsive transitions, keyboard return, browser gates, inspection, report assertions, and cleanup. The server logs request and live connection counts. Cleanup closes the test-scoped page and context first, calls `server.close`, then `server.closeAllConnections`, awaits the close callback, and removes only the fixture's temporary root. Cleanup continues through each step if one step fails. An original assertion error is logged and rethrown after cleanup; cleanup errors are logged without replacing it. If the body succeeded, cleanup errors fail the test.
