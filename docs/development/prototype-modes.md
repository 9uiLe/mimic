# Current and Proposed prototype modes

`buildPrototypeModes(store, modePlan, outputRoot)` builds two specification prototypes from explicit render plans for one exact scenario. The caller authors the plans and a separate mode plan. The mode plan is a non-artifact input, not a revision or approval of the Product UI Contract. Its canonical SHA-256 digest and exact references are saved in `comparison/mode-plan.json` and `comparison/comparison.json`; the generated bundles live under `comparison/current/` and `comparison/proposed/`. Each bundle still carries its own render-plan digest and source locks.

The canonical Product UI Contract schema has no structured current, required, proposed, or unresolved fields. S05 conveys those distinctions in prose and provenance. The mode plan declares each choice with a status and exact System Capability reference. Noncurrent choices also carry an exact System Request reference. Its explicit bindings assign every authored text value, fixture use, and action in every state to one choice by state, node path, and field. Unused fixture values and unbound values are rejected. Proposed must retain each bound Current node relationship, including a control's label, component, and transition together. A binding is an authored, reviewable claim about meaning; no parser can prove that its chosen capability describes the text. Both modes must reference the same scenario revision.

When a bundle has a [responsive program](prototype-responsive.md), each operation also needs one `responsiveOperation` binding with its state and zero-based operation index. This atomic binding classifies the operation's group label, DOM behavior, replacement subtree, component and action together under one choice. Replacement fixture values must be used and bound through that operation; its signature includes each resolved value, so different Current and Proposed labels cannot share a binding by changing only a fixture. An unbound operation is rejected; Proposed cannot remove a bound Current operation. The generated Proposed notice is appended outside disclosure targets and remains visible on mobile. Rejected System Requests still publish only Current.

- **Current** uses only fresh, approved System Capabilities with `availability: current` and supporting evidence. A fact provenance entry for the capability description must name the supporting evidence. The exact Current capability is locked by the approved UI Contract and named in derived provenance for a relevant contract content field. The approved scenario locks that contract. Artifact-store dependency checks enforce registered scope ancestry, allowing a domain scenario to consume parent-product inputs while rejecting sibling-product dependencies. The store verifies human authority and exact locks; evidence relevance still needs review.
- **Proposed** may add approved required choices whose proposed capability and System Request are both approved, and explicitly proposed choices with a pending or approved System Request. The capability locks that request and names it in derived provenance; the request locks the contract, names it in derived provenance, and has `changeType: capability`. Every generated state visibly labels noncurrent choices, the System Request ID and revision, and a shortened digest. The full digest is in the saved plan and comparison manifest. Synthetic fields and actions remain labeled as unimplemented.
- **Unresolved or rejected** proposed choices cause the Proposed build to fall back to the Current build. A live comparison must supply an exact decision-context request revision for every noncurrent choice. A newer rejected revision triggers fallback; a newer nonrejected revision requires an explicitly revised choice. The caller is responsible for supplying the authoritative current decision revision; the builder never resolves a floating latest revision. Historical replay uses `decisionContext.kind: historical` and is labeled in the comparison manifest. The saved plan preserves the authored proposed intent without rewriting canonical artifacts.

The mode wrapper validates paths, relationships, and bindings before creating output. It builds through the existing builder in a private staging directory, then publishes the whole comparison directory with one rename. The comparison path and both bundle names must be single safe directory names; any existing comparison destination is rejected without removal, including one containing stale Proposed output. A failed build cleans staging, so a corrected plan can retry with the same unused destination. The trusted local output root must not be subject to hostile concurrent renames, as described in [Prototype Builder](prototype-builder.md). Neither prototype is production code, and artifact approval does not approve the authored mode or render plan.

Each saved bundle plan retains its authored `outputPath` relative to the comparison directory (for example, `current`), because the builder seals that plan and its digest before the wrapper publishes the comparison directory. The returned bundle directory is under the trusted root at `comparisonPath/outputPath`. Quality gates verify that location against the saved mode plan and comparison manifest; they do not rewrite the saved render plan or its digest after publication. A fallback comparison publishes only Current, while retaining the authored Proposed intent in `mode-plan.json`.
