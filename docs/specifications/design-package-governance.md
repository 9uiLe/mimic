# Design Package storage, versioning, and asset governance (v1)

Status: architecture specification for [9UI-95](https://linear.app/9uile/issue/9UI-95/specify-design-package-storage-versioning-and-asset-governance), under [9UI-82](https://linear.app/9uile/issue/9UI-82/m0-codify-mimic-v1-architecture-and-operating-model). This contract follows the [Mimic v1 Architecture & Operating Reference](https://linear.app/9uile/document/mimic-v1-architecture-and-operating-reference-4b4a6ddcb408), the [technical baseline](technical-baseline.md), and the [artifact architecture](artifact-architecture.md). It supplies the package boundary for [9UI-115](https://linear.app/9uile/issue/9UI-115/implement-design-package-compiler-and-immutable-release-pipeline) and the resolution boundary for [9UI-116](https://linear.app/9uile/issue/9UI-116/implement-package-registry-abstraction-design-lock-and-version-compatibility).

## Storage and authority boundaries

The Design Engine's source repository holds engine code, schemas, and maintained knowledge. A user's or product's design workspace and Design Package history belong to separate user/product repositories or storage. Engine commits are not package identities, and a package release does not alter the engine repository. Git and the filesystem are the initial workspace and history backing stores. Registry, acquisition, integrity checking, and storage are logical responsibilities so another backing store can implement this contract without changing package identities. No particular directory layout, runtime class, API, or registry service is prescribed here.

Three kinds of material have different mutation rules:

| Material                | Purpose                                                                                | Mutation and authority                                                                                                                                                       |
| ----------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Design working state    | Active product exploration, draft files, provisional artifacts, and generated previews | Mutable; approval and locking still protect approved artifact snapshots in place.                                                                                            |
| Reusable assets         | Scoped Design System and other governed material intended for reuse                    | Identified and versioned independently; promotion and release follow human gates. A draft of a new version may change, but an approved snapshot or released version may not. |
| Released Design Package | A product's approved design deliverable and exact dependency selection                 | Immutable package version and bytes after human approved release. Any changed inventory, lock, file, or decision produces a new release version.                             |

The deliverable is framework-neutral. Its executable prototype uses semantic HTML, plain CSS, and ES JavaScript. Production-framework conversion and production application generation are outside Mimic's package contract.

## Package inventory and identity

A release manifest is the logical inventory of what the package asserts and delivers. It identifies the package's logical ID, exact release version, mode, product and ownership context, approval reference, included files with integrity information, exact artifact references, and exact external package/asset dependencies. It accounts for these categories, including an explicit absence or not-applicable explanation when a category has no deliverable:

| Category                      | Inventory responsibility                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Product foundation            | Product definition, user/task model, brand, and design principles.                                                        |
| Experience structure          | Experience Domains, cross-domain journeys, and selected architecture or design direction.                                 |
| Design System                 | Exact asset usage and product/domain/local extensions, source tokens, semantic icon meanings, and provider bindings.      |
| Interface and system boundary | Product UI Contract and System Requests, distinguishing approved current capability from proposed change.                 |
| Prototype                     | Executable framework-neutral HTML/CSS/ES JavaScript and its fixtures or mock data, with their provenance and limitations. |
| Scenarios                     | Scenarios used to inspect intended interaction and behavior.                                                              |
| Quality                       | Quality findings and validation reports with evidence references and unverified claims identified.                        |
| Decisions                     | Decision Records, approval references, and supersession links sufficient to follow selected outcomes.                     |
| Handoff                       | Implementation guide explaining interpretation and known constraints without converting to a production framework.        |

For a registered Product-scoped `design` package, the explicit inventory may contain artifact snapshots originally scoped to that Product's registered Domain and Local descendants, alongside its own and ancestor artifacts. This is delivery containment: each artifact retains its original scope, ID, revision, digest, approval, freshness, and provenance. Cross-domain journey `content.domains` values describe experience domains; they do not create artifact dependency locks. Artifact and package dependency consumption still follows the ancestor direction below. Containment does not promote an asset or authorize a broader reuse scope. Other package kinds and scopes retain the ancestor-only artifact containment rule. See [the multi-domain package contract](../development/multi-domain-package-contract.md).

An **artifact reference** names a logical artifact ID and exact integer revision, its schema version, and locked integrity digest; the artifact schema defines the artifact's own content and lifecycle. **Package metadata** names a package ID, its Semantic Versioning release, mode, ownership, approval, and manifest inventory. A **bundled file** is a particular set of bytes, named by a package-relative location and checked by integrity data. These are different things: a manifest entry for a prototype file is not an artifact revision, a package version is not an artifact schema version, and listing an artifact does not imply its bytes are bundled. For every entry, the manifest makes inclusion versus external resolution explicit. The package and lock together account for the transitive material needed to interpret the release, including applicable schema versions and licenses for third-party assets.

## Distribution modes

Each mode is recorded in its own immutable, versioned manifest and lock. A `(logical package ID, release version)` fixes the mode and included bytes at publication; distributing the other mode requires a separately approved release version or package ID. Mode affects which dependency bytes travel with the release, not which artifact or dependency versions are selected.

| Mode              | Included                                                                                                                                                                                            | Referenced and acquisition requirement                                                                                                                                                                          | Portability limit                                                                                                                                                                                     |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reference Package | Manifest, `design.lock.yaml`, package-owned artifacts and deliverable files, including the runnable prototype, fixtures, reports, and guide where applicable                                        | Reusable Design System assets and other external dependencies may remain outside the bundle. Every external edge selects an exact version or artifact revision and digest and identifies an acquisition source. | Reconstruction requires access to those exact external bytes and applicable licenses. A link that now serves changed bytes or disappears is insufficient.                                             |
| Portable Snapshot | Everything in the Reference Package plus the exact dependency files required to interpret, inspect, and run its declared deliverables without resolving package dependencies from a remote registry | External provenance, original IDs, versions, and license obligations remain recorded even for bundled copies. Runtime prerequisites such as a compatible browser remain documented.                             | Portable within declared platform and licensing constraints; it does not imply a production application, vendor assets that cannot be redistributed, or independence from all execution environments. |

For either mode, reconstruction starts from the immutable manifest, verifies the package-owned files, resolves each locked external dependency at its exact ID and version, verifies acquired bytes against the lock, and then interprets the selected artifact revisions and runs the prototype with the declared fixtures. A missing dependency, mismatch, incompatible schema, or prohibited distribution blocks a reproducibility claim and must be reported. A mutable URL is only a retrieval hint; it never substitutes for an exact version and verified integrity. A Portable Snapshot may be emitted only when all required distributable dependency bytes can actually be included. Otherwise use Reference Package and state the acquisition requirements; do not label a partial bundle portable.

### Illustrative packaging example

The following is an inventory sketch, not a proposed YAML schema. **All shortened digests are illustrative and unverified.**

| Item                       | Reference Package `catalog/1.2.0`                                                            | Portable Snapshot `catalog/1.3.0`                                                    |
| -------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Selected direction         | `art_direction` revision 4, schema `1.0.0`, digest `sha256:…a4` included                     | Same exact approved artifact included                                                |
| Product UI Contract        | `art_ui_contract` revision 2, digest `sha256:…b2` included                                   | Same exact approved artifact included                                                |
| Organization tokens        | `org/tokens` version `2.3.1`, digest `sha256:…c1` referenced in lock and acquired separately | Same version and digest; required distributable token bytes bundled, origin retained |
| Semantic icons and binding | `org/icons` version `1.4.0`, digest `sha256:…d0` referenced with provider/license data       | Same exact bytes bundled only if its license permits redistribution                  |
| Prototype                  | `prototype/index.html`, CSS, JavaScript, fixtures, and each file's digest included           | Identical package-owned files included                                               |

These separately approved releases select the same design and dependency versions. Bundling dependency bytes in the later portable release does not upgrade or reinterpret them, and the earlier reference release remains unchanged. A real release must carry full verified digests; the shortened values above must never be used as locks.

## Scope, distribution, and promotion

Resolution follows **Organization → Product → Domain → Local** parentage. An asset retains a stable logical identity and owning scope; scope is not inferred from a path. A product can consume an organization asset at an exact version, a domain can consume product or organization material, and local work can extend its ancestors. Local overrides or extensions do not silently mutate their ancestor. Same-named assets require an explicit resolved ID, scope, and version to avoid accidental shadowing.

Promotion is a reviewed distribution change, not a path move or implicit scope widening. A Local asset promoted to Product must receive human approval. Promotion from Product to Organization requires a separate human approval; Local cannot bypass Product by publishing directly to Organization. Domain-scoped material must first be explicitly adopted at Product scope before any Organization promotion. Approval records identify the source snapshot, proposed destination scope and owner, compatibility and license review, human actor, and resulting destination asset/version. The original source and its consumers remain locked to their existing versions unless separately changed.

For example, `local/button-density` can be proposed as `product/button-density` after usage and accessibility review. A human approves the Local → Product promotion, creating a separately identifiable Product version. Later reuse across products can motivate Product → Organization, with its own human review and release. Neither approval edits a locked Local consumer or grants approval for the next promotion.

## Exact resolution and lock responsibility

`design.lock.yaml` is the conceptual **product design dependency lock**, separate from the monorepo's `pnpm-lock.yaml`. It records the resolved dependency graph for a package version: stable logical IDs and owning scope, exact reusable package versions, exact artifact IDs and integer revisions, schema versions needed for interpretation, provenance/acquisition locations, and integrity for selected artifact snapshots and files. It includes transitive dependencies and identifies what is bundled versus externally acquired. A resolver verifies existence, allowed scope, compatible schema and license constraints, exact identity/version, graph consistency, and digest equality before compilation or reconstruction. A missing or conflicting exact version is an error, not permission to fall back to another version.

The manifest selects what the package delivers; the lock proves what each dependency edge resolved to. The registry maintains unique `(logical ID, exact version)` and `(artifact ID, revision)` identities, immutable approved/released snapshots, and retrievability or a clear unavailable result. Paths, URLs, and Git SHAs may locate or audit data but are not sole identity or version authority. This specification does not define byte canonicalization for artifact digests or choose a particular owned storage service; until the relevant storage rule exists, example digests cannot be claimed verified. A verifier must refuse an unverifiable integrity claim.

There is no canonical `latest` dependency and no automatic Design System upgrade. Discovery may recommend currently suitable versions for a **new** product. Existing products and released packages retain their exact locks. A different dependency version enters an existing product only through an explicit proposed change, impact review, validation, and the required human approval for durable changes or release. An impact classification of `NONE`, `SAFE`, `REVIEW_REQUIRED`, or `BREAKING` describes expected compatibility work; even `NONE` or `SAFE` does not grant approval or rewrite a lock. These package upgrade labels are distinct from artifact dependency `onChange` (`none`, `validate`, `revise`, `invalidate`) and artifact freshness.

For example, a product locked to `org/tokens@2.3.1` may be offered `2.4.0` as `SAFE`. The proposal compares token use, generated CSS, icon bindings, affected prototypes, and validation. If approved, a new product lock and package release may select `2.4.0`; `catalog/1.2.0` and its `2.3.1` lock stay unchanged. If review fails or approval is pending, the existing exact version remains selected.

## Version and history semantics

Reusable released packages and Design Packages use Semantic Versioning (`MAJOR.MINOR.PATCH`) as separate version sequences per logical package ID. A change that breaks the declared consumer contract requires a major version; compatible additions use minor; compatible corrections use patch. Every release version is immutable and requires the applicable human release decision. Version comparison helps communicate compatibility but cannot itself prove compatibility or authorize release. The version of an individual reusable asset is selected through its owning released package or independently versioned asset identity, as applicable; no floating version range is stored in a released lock.

`meta.schemaVersion` describes an artifact's structural contract. `meta.revision` is an integer snapshot sequence for one artifact ID. A Git commit records repository history; a path locates a file. None is interchangeable with a package Semantic Versioning release. A newer package may select the same artifact revisions, and a new artifact revision does not automatically create a release.

Decision Records preserve immutable history. A later decision explicitly supersedes an earlier decision and records the reason and human authority where required; it does not overwrite the earlier record or retroactively change a released package. For example, `art_decision_nav` revision 3 in `catalog/1.3.0` remains part of that release. A newly approved decision `art_decision_nav` revision 4 supersedes revision 3; a later `catalog/1.4.0` may select revision 4 and record both the decision replacement and `catalog/1.3.0` as its predecessor release. Consumers of `1.3.0` still reconstruct revision 3 and its original package bytes. This same rule applies to approved asset snapshots and package files.

## Asset status and removal

Asset **distribution lifecycle** is `experimental → candidate → approved → released → deprecated → removed`. Experimental assets support local exploration; candidate assets are proposed for broader use; approved assets have the required human acceptance; released assets are available as exact immutable versions; deprecated versions remain identifiable but are discouraged for new selections; removed versions leave future discovery and selection. Transitions that broaden shared distribution or release require the relevant human approval. Deprecation and removal must carry recorded reasons and impact on consumers.

This distribution lifecycle is independent of an artifact revision's `provisional/proposed/approved/rejected` lifecycle and its `valid/stale/blocked` freshness. An asset can have a released version whose underlying artifact revision later receives a stale assessment; the assessment is a recorded event or new revision, not a mutation of released bytes. A removed asset must not silently break an existing exact lock or rewrite historical releases. Resolution must still verify and reconstruct an already locked release when its bytes are available, or clearly report that the dependency cannot be acquired. This contract does not grant physical deletion, set retention periods, or authorize destruction of historical bytes.

## Implementation boundaries and open contracts

[9UI-115](https://linear.app/9uile/issue/9UI-115/implement-design-package-compiler-and-immutable-release-pipeline) must compile the declared inventory and both modes, verify inclusion and lock integrity, enforce immutable approved releases and human release authority, and report incomplete portability. [9UI-116](https://linear.app/9uile/issue/9UI-116/implement-package-registry-abstraction-design-lock-and-version-compatibility) must provide exact identity/version/revision resolution, lock verification, scope and promotion checks, compatibility reporting, and historical lookup behind replaceable storage. Both consume the artifact contracts without changing their schemas here.

Before an implementation can claim verified artifact or package digests, the owner of storage/integrity work must specify byte canonicalization, digest coverage, and how a released snapshot is retained or acquired. Before promising long-term retrieval after removal, governance must decide retention and any deletion authorization. These are contract gaps for the owning follow-on work or an owner **Human Decision** issue if a durable policy choice is required; no retention period, deletion permission, or storage provider is implied here. Work that does not depend on those choices can proceed.

This specification does not set [9UI-89](https://linear.app/9uile/issue/9UI-89/) Run states or commit-point mechanics, [9UI-92](https://linear.app/9uile/issue/9UI-92/) Design System payload, property, or icon rules, or [9UI-96](https://linear.app/9uile/issue/9UI-96/) tooling. Those contracts can evolve independently while respecting this package boundary.
