# Orchestrator, Runs, and Human Commit Points (v1)

This specification defines the orchestration contract for [9UI-89](https://linear.app/9uile/issue/9UI-89/specify-orchestrator-runs-and-human-commit-point-semantics). It follows the [Mimic v1 architecture and operating reference](https://linear.app/9uile/document/mimic-v1-architecture-and-operating-reference-4b4a6ddcb408) and consumes the [artifact architecture](artifact-architecture.md) and [technical baseline](technical-baseline.md). Runtime implementation and the per-Skill I/O catalog are separate work. Terms below describe observable decisions and guards; they do not prescribe a database, CLI payload, or storage path.

## Authority and starting context

The controlling AI agent invokes the Orchestrator through the Mimic CLI/filesystem protocol. The Orchestrator routes artifact references to Skills and receives their outputs; Skills do not call one another. System-first, Experience-first, and Hybrid select where a Run begins its investigation. They are **entry modes**, not separate pipelines, authorities, artifact types, or exemptions from the shared Product UI Contract and human gates. All paths converge through the common product and domain contracts before dependent design work.

Before generating an artifact, resolve applicable reusable artifacts and approved canonical revisions at organization, product, domain, then local scope. Record which exact revisions were reused, why each was applicable, and any gaps. Prefer an applicable approved asset to generating a duplicate. A proposed or rejected asset is not an approved substitute. A newer revision is a candidate for explicit adoption, not an automatic upgrade. If no approved artifact fits, create a provisional candidate and make any durable choice a proposal. The Orchestrator must not silently replace a locked dependency because an entry mode suggests a different starting point.

AI may autonomously analyze, retrieve, explore alternatives, draft artifacts, build prototypes with labeled mock data, critique, and run checks while effects remain reversible within a Run. Product definition, brand, Experience Domain boundaries, selected design direction, system changes, promotion to shared organization scope, and release are **PROPOSE_ONLY**. Policy must refuse silent overwrites of approved or locked assets, claims that proposed capabilities are current, invented empirical evidence, and release without final human approval. A valid schema or convincing output does not confer authority.

## Run and state dimensions

A **Run** is an identifiable, reversible provisional branch from a recorded canonical design state. Its base is a set of exact canonical artifact IDs, revisions, and verified lock digests, plus the intended scope and entry mode. Work in that branch can produce new provisional revisions, evidence, prototypes, proposals, and revision requests. It does not change canonical selection by itself. Its identity is distinct from an artifact ID, Git commit, file path, and Design Package version. The registry/storage implementation may use Git; consumers rely on logical IDs and locks.

The Run's state describes orchestration progress only:

| Run state      | Meaning                                                                                                                          |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `active`       | At least one authorized reversible action can proceed, and no proposal set is ready for a Human Commit Point.                    |
| `review-ready` | At least one proposal set is ready for a Human Commit Point; safe provisional work may still proceed under recorded assumptions. |
| `blocked`      | No proposal set is ready and no safe work remains; a specific missing fact, authority, or integrity check is recorded.           |
| `closed`       | No further work occurs on this branch; its close record states which proposals merged or were discarded and why.                 |

An individual work item can be blocked while the Run remains `active` or `review-ready` if other safe work exists. Queue nonblocking durable choices for a later Human Commit Point and continue provisional exploration; interrupt the human only when the missing answer genuinely blocks all remaining safe work. A Human Commit Point is scoped to an explicit proposal set; one Run may have more than one such point. `review-ready` does not imply human approval or a paused Run. A closed Run cannot be reopened by changing its state; later work starts a new Run from the then-current canonical state.

These dimensions remain separate from Run state:

| Dimension                      | Existing values                                   | Orchestration interpretation                                                                                                         |
| ------------------------------ | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Artifact `lifecycle.status`    | `provisional`, `proposed`, `approved`, `rejected` | The artifact revision's review state. A provisional Run may contain several such revisions, including rejected history.              |
| Artifact `lifecycle.freshness` | `valid`, `stale`, `blocked`                       | The revision's current usability assessment; stale or blocked needs a reason and a recorded state event or revision.                 |
| Artifact `approval.status`     | `pending`, `approved`, `rejected`                 | The human approval envelope; approved/rejected records need decision ID, human actor ID, and time.                                   |
| Decision `content.outcome`     | `open`, `proposed`, `committed`                   | The decision payload's progression. A rejected proposal is recorded by rejected lifecycle/approval and history, never a new outcome. |

Approval of a decision artifact with `content.outcome: committed` requires an approved envelope and a chosen alternative with rationale. A proposed or open decision does not authorize dependent durable action. Rejection remains visible in the artifact envelope and decision history. Any renewed alternative must be an explicitly new proposal/revision that cites the prior rejection and its reason; replaying the rejected candidate as if pending or approved is forbidden.

## Transition guards and effects

Each transition is an auditable event with Run ID, actor, time, input and output artifact references, and reason. Implementations may store events differently, but must preserve their order and the state reconstructed from them. Guards are evaluated against current canonical selection and verified exact dependencies at the point of effect, not merely against the Run's original snapshot.

After any event that changes remaining work, derive the next Run state in this order: `review-ready` if any valid proposal set is still ready; otherwise `active` if any authorized reversible action remains; otherwise `blocked` if an unresolved blocker remains; otherwise `closed`. A rejected or discarded proposal does not count as ready. This rule applies to partial commit decisions and to work blocked independently of the proposal under review. Explicit `discard-run` closes the branch only after recording the fate of every unmerged proposal.

| Current Run state                   | Event / actor                               | Guard                                                                                                                                                                  | Effect and next Run state                                                                                                                                           |
| ----------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| New                                 | `start` / agent                             | Scope and entry mode known; canonical base resolved; every referenced approved revision and lock verified.                                                             | Record Run/base and reuse decisions; derive state from available work. Missing reusable context is investigated before generation.                                  |
| `active`, `review-ready`            | `produce-provisional` / agent or Skill      | Operation is reversible; inputs resolve to exact revisions; policy permits the action; unknowns are labeled.                                                           | Add provisional artifact/evidence/prototype on branch, with provenance and dependency locks; derive next state from remaining work.                                 |
| `active`, `review-ready`            | `submit-proposal` / agent                   | Durable choice is marked PROPOSE_ONLY; proposal names affected canonical revisions, alternatives, rationale, evidence limits, and dependents.                          | Record proposed revision with pending approval and an explicit Human Commit Point set; enter `review-ready`. Existing approved revision remains canonical.          |
| `active`, `review-ready`            | `encounter-unknown` / agent                 | Unknown truly prevents the affected next action; no honest safe assumption resolves that action.                                                                       | Record missing fact and affected work; queue a human decision (Linear issue labeled `Human Decision` where available). Derive next state from remaining work.       |
| `blocked`                           | `resolve-blocker` / human or verified input | Resolution is recorded with evidence or human decision; exact inputs and policy rechecked.                                                                             | Record resolution or remaining blocker; derive next state from remaining work. No fabricated answer.                                                                |
| `review-ready`                      | `commit-point-approve` / human              | Explicit human identity and decision; selected proposal set validated; exact base/dependencies and current canonical state rechecked; no conflict or forbidden effect. | Record approved envelopes and decision history; merge only named revisions into canonical selection atomically for that set; derive next state from remaining work. |
| `review-ready`                      | `commit-point-reject` / human               | Human rejection identifies the proposal set and rationale.                                                                                                             | Record rejected envelopes/history; discard its proposed effects, retain prior canonical selection; derive next state from remaining work.                           |
| `review-ready`                      | `commit-point-revise` / human               | Human requests changes without approving the existing set.                                                                                                             | Record feedback; keep candidate noncanonical, create a new provisional/proposed revision for changed content; derive next state from remaining work.                |
| `active`, `review-ready`, `blocked` | `discard-run` / human or authorized agent   | No unreconciled canonical effect is removed; proposal outcomes and reasons are retained.                                                                               | Discard unmerged branch effects, retain immutable decision/audit history, then `closed`.                                                                            |

At a commit point, an approval applies to the named revision set only. Partial acceptance or rejection must enumerate each affected proposal and preserve the resulting history; do not imply that approval of one artifact approves its siblings or a release. A conflict, stale finding, invalid lock, or newly forbidden effect prevents that merge until resolved through a new proposal or explicit human action. Closing records the accepted, rejected, and discarded outcomes independently; the Run state itself is not an artifact lifecycle or decision outcome.

### Guards across revisions

1. Validate the artifact schema and registry invariants, provenance references, scope ancestry, and human decision identity before promotion. Approved snapshots are immutable in place. Editing their content, dependencies, or digest requires a new revision with `meta.supersedesRevision`; approval is recorded for that new revision, leaving the old snapshot intact.
2. Resolve each `dependencies[]` entry as its exact `artifactId`, `revision`, and `lockDigest`. A mismatch at that revision is an integrity failure and blocks use regardless of `onChange`. Canonical digest computation and byte serialization belong to storage, not the Orchestrator; it consumes verified results and must not manufacture a digest.
3. A newer upstream revision leaves the existing lock intact. Apply the declared `onChange` minimum response when considering it: `none` records no content impact; `validate` rechecks; `revise` produces a proposed downstream revision; `invalidate` blocks use until replacement or human resolution. Only an explicit new downstream revision may adopt the new exact upstream revision and digest.
4. If downstream critique, prototype, or validation exposes an upstream problem, record an appropriate upstream revision request with evidence and affected locks (`system-request` for a system change). Route it to the owner/review path. Do not mutate an approved upstream revision or silently retarget downstream dependencies. Continue independent work only under labeled provisional assumptions.
5. If canonical selection moved since the Run began, compare the proposed effect with current state and all affected exact locks before merge. Rebase by creating/reviewing new revisions where needed; never silently overwrite or treat a stale proposal as accepted. A rejected candidate is not eligible for automatic resurrection.

## Stable boundary for Skills and later implementation

The Orchestrator supplies a Skill with a task intent, scope, Run ID, applicable exact input artifact references and locks, unresolved assumptions, and allowed authority (`AUTONOMOUS` or `PROPOSE_ONLY`). It checks that the Skill's returned artifact references, evidence/provenance, dependency declarations, proposed decisions, and blocked reasons fit the artifact contract and Run policy before routing another task. A Skill cannot approve its own output, change canonical selection, invoke another Skill, or release. The Orchestrator maintains the dependency graph and performs policy/commit guards; each Skill performs its bounded design task. The later Skill contract defines concrete per-Skill inputs and outputs without changing these authority or state semantics.

The Orchestrator's user-facing status must distinguish available reversible next actions, proposals awaiting human choice, genuinely blocked work, and evidence gaps. Large artifacts stay file-backed; compact status exposes IDs, paths, and next actions. It must never present provisional design claims or mock observations as verified facts. Empirical results without supporting evidence remain `UNVERIFIED`; automated accessibility checks are limited evidence and cannot alone establish WCAG 2.2 AA conformance.

## Conformance examples

| Situation                                                                                                        | Required behavior                                                                                                                              |
| ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| System-first Run finds an applicable approved product token asset                                                | Reuse its exact approved revision and verified lock before generating a visual candidate; the entry mode grants no replacement authority.      |
| Direction choice is pending, but two reversible prototypes can test different directions                         | Keep the Run `review-ready` and explore both provisionally, identifying each assumption and preventing either from becoming canonical.         |
| A missing production capability makes a specific flow unsafe to represent                                        | Mark the flow blocked, request a human/system decision, and continue unrelated critique if possible. Never label the capability current.       |
| Validation finds an approved upstream domain boundary inadequate                                                 | Record an upstream revision request and affected downstream locks; propose a new boundary revision through a Human Commit Point.               |
| Human rejects a proposed direction                                                                               | Preserve rejection envelope/history and prior approved direction. Any later reconsideration is a new explicit proposal with rejection context. |
| Human rejects proposal A; only genuinely blocked task B remains                                                  | Set the Run to `blocked` with B's reason, rather than `active` or `closed`.                                                                    |
| Human approves proposal A; proposal C is still ready for review                                                  | Keep the Run `review-ready` for C. A's approval does not decide C.                                                                             |
| New design-system revision exists while a Run uses an older approved lock                                        | Keep the older exact lock until a new downstream revision explicitly adopts the newer one after impact handling.                               |
| Agent attempts to edit approved bytes, accept its own proposal, invent test evidence, or release unapproved work | Refuse the operation and record the reason. No schema pass, Run state, or entry mode overrides these guards.                                   |
