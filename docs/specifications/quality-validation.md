# Design quality and validation (v1)

This specification defines the Design Quality Architecture for [9UI-93](https://linear.app/9uile/issue/9UI-93/specify-quality-gates-validation-evidence-and-revision-routing). It applies the [Mimic v1 architecture and operating reference](https://linear.app/9uile/document/mimic-v1-architecture-and-operating-reference-4b4a6ddcb408) to the [artifact contracts](artifact-architecture.md), [Run and Human Commit Point rules](orchestrator-runs.md), [design-space exploration](design-space-exploration.md), and [Design Package inventory](design-package-governance.md). It specifies judgments and routing, not new artifact fields, Skill invocation envelopes, runtime transitions, validators, fixtures, or CI commands. The versioned schemas remain authoritative for data shape.

## Quality decisions and scope

Assess each applicable criterion against an exact artifact revision, prototype revision or identified file snapshot, and the action that would rely on it. State and severity are separate axes:

| State        | Meaning                                                                                                                                                  |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PASS`       | The stated criterion passed within the documented method and conditions. It makes no claim beyond that scope.                                            |
| `CONCERN`    | Evidence identifies a material risk or partial satisfaction, but does not establish failure of the whole criterion. State the unresolved condition.      |
| `FAIL`       | Evidence establishes that an applicable criterion was not met under the stated conditions.                                                               |
| `UNVERIFIED` | An applicable criterion lacks sufficient evidence for a pass, concern, or fail. Record the missing method or observation and the action depending on it. |
| `N/A`        | The criterion genuinely does not apply to the target and intended use. State why.                                                                        |

| Severity  | Meaning                                                                                               |
| --------- | ----------------------------------------------------------------------------------------------------- |
| `BLOCKER` | The finding prevents a specified affected action until resolved; identify that action and its reason. |
| `MAJOR`   | Material impairment or risk requiring revision or explicit review before the affected durable choice. |
| `MINOR`   | Bounded defect or improvement that can be tracked without invalidating the intended outcome.          |
| `NOTE`    | Context, limitation, or opportunity with no asserted defect.                                          |

Severity is not a substitute for state: `UNVERIFIED` can be `BLOCKER` when evidence is mandatory for a high-risk action, and `FAIL` can be `MINOR` when its impact is narrow. `N/A` requires a genuine nonapplicability rationale; it cannot hide an applicable failed or unperformed check. An applicable test that was planned but not run is `UNVERIFIED`. Do not turn an observed failure into `UNVERIFIED` because a later check is pending. Record criteria individually, with qualitative reasons and evidence limits. There is no synthetic overall design score, numeric quality rollup, or Design System reuse-rate quality KPI. Reuse is governed by applicability and exact locks; a high reuse percentage does not establish suitability.

Risk determines validation depth before a durable choice or release: consider potential harm, reversibility, novelty, uncertainty, exposure, and the strength of existing evidence. A low-risk, reversible prototype may proceed under labeled assumptions. A critical task, accessibility barrier, irreversible choice, or untested production assertion demands a stronger method and appropriate human or empirical evidence. Record the chosen depth and remaining limits; do not claim that every criterion needs the same study or that a passing automated check closes higher-risk questions.

## Three evidence layers

| Layer                          | Useful methods and supported conclusion                                                                                                                                                                                              | Limit                                                                                                                                                                                                          |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deterministic validation       | Parse and schema checks, exact-reference and lock checks, static source checks, build checks, and automated prototype tests can establish that specified inputs satisfy their executable rules in a recorded environment.            | A schema-valid reference can be irrelevant, stale, or unsupported. Passing executable checks does not establish usability, visual quality, user behavior, or complete accessibility conformance.               |
| AI design critique             | Inspect task fit, information structure, interaction behavior, domain and journey continuity, risk, accessibility concerns, design-system fit, and structural diversity; produce criterion-specific reasons and testable hypotheses. | Critique is an analysis of artifacts, not an observation of users or proof of compliance. Model confidence is not evidence.                                                                                    |
| Human and empirical validation | Human review records a decision or informed assessment; research, task observation, and representative accessibility testing can support claims about actual use under the documented participants, devices, tasks, and conditions.  | Human approval is authority for a named decision, not evidence that an untested claim is true. A small or unrepresentative study supports only its stated scope; missing empirical support stays `UNVERIFIED`. |

The accessibility baseline is WCAG 2.2 AA for the applicable prototype and interaction. Automated accessibility checks establish results for their rules, pages, states, and environments only. They cannot by themselves prove full WCAG 2.2 AA conformance; manual inspection and relevant human testing must cover criteria and interaction states automation cannot decide. A failure in a covered rule remains `FAIL` even when other checks pass.

When mobile use is required, the primary goal must remain achievable on mobile with appropriate interaction and content, not merely fit a viewport. Evaluate the goal, steps, critical information, navigation, state, and recovery in representative mobile conditions against the intended desktop or canonical flow. Record differences that matter to task success. When mobile is outside the approved product scope, explain `N/A` rather than silently omitting the criterion.

Design directions must differ in underlying task structure, interaction model, information organization, temporal behavior, or another problem-relevant mechanism. Different colors, type, imagery, or component styling alone do not count as structurally diverse directions. Critique the mechanism and trade-offs against the problem profile before human selection; do not treat reference distance or visual variety as a quality score.

## Evidence record and existing artifacts

A reviewable claim connects the **exact target artifact ID and revision** (or identified prototype/file snapshot), **criterion**, **method**, **source or resolvable evidence reference**, **conditions**, **result**, and **limitations**. Conditions include relevant tasks, viewport/device, environment, participants or reviewer role, and time when they affect interpretation. Explain how the source supports the criterion; existence, schema validity, or an evidence link alone is not substantive support. Record assumptions, unknowns, and derived claims honestly. A newer target revision requires reassessment of affected claims rather than carrying forward a prior `PASS` by name.

The existing `evaluation` content has `summary`, `target`, and `findings`; each finding has only `criterion`, `state`, `severity`, and `reason`. The `reason` states the observed issue, impact, uncertainty, and affected action in concise prose. Do not add `evidenceRefs` or other properties to a finding. Link a narrow finding through envelope `provenance` at `/content/findings/<index>` and associated `validation` artifacts or external evidence references. Use the existing provenance kinds correctly: a `fact` needs an evidence reference, a `derived` claim needs input references, and an `unknown`, `assumption`, or `hypothesis` needs a rationale. Reviewers still verify relevance and exact target identity; the schema only checks shape.

The existing `validation` content has `summary`, `target`, `method`, `state`, `evidenceRefs`, and optional `limitations`. `PASS`, `CONCERN`, and `FAIL` require at least one evidence reference. Resolve each reference and inspect what it actually shows. `UNVERIFIED` may have no evidence or inconclusive evidence; describe the gap in the summary, method, or limitations. `N/A` records why the method or criterion does not apply. For several criteria or methods, use distinct reports or clearly scoped targets and summaries so one result is not mistaken for blanket validation. The existing `system-request` content is for a proposed **system change** (`changeType`, `request`, `rationale`); it is not the generic container for brand, product, domain, or direction critique.

The schema fields are the machine-readable minimum. Traceability, evidence relevance, coverage, conditions, and action gating are semantic obligations for authors and reviewers. They do not imply new fields or that current tooling enforces them. The [valid evaluation and validation fixtures](../../fixtures/artifacts/valid) illustrate permitted shapes, including a planned review that remains `UNVERIFIED`; they are not evidence that a design passed.

## Gates and action routing

For each finding, name the **affected action**: continuing a particular provisional task, submitting a proposal, merging a named proposal set at a Human Commit Point, or releasing a Design Package. An integrity failure such as an unresolved exact lock or digest mismatch blocks use of that input. A demonstrated critical task or accessibility failure blocks advancing the affected design as though it satisfied the criterion. A required high-risk empirical claim without evidence blocks relying on that claim for a durable choice or release. The same finding need not block independent critique or a separate reversible prototype that labels the uncertainty. Record the failed or missing criterion and a concrete resolution condition; do not use a `BLOCKER` severity label as an automatic Run-wide switch.

A proposal is reviewable when its applicable checks, known failures, evidence limits, alternatives, and affected dependencies are disclosed and it satisfies the [Run submission guards](orchestrator-runs.md). A proposal that depends on a false capability, invalid lock, or missing evidence essential to the claimed outcome is not mergeable or releasable merely because a reviewer is present. At the commit point, recheck current canonical selection and exact dependencies. A human may approve a bounded decision with disclosed uncertainty when policy permits, but approval cannot create missing observations, make a failed check pass, rewrite approved bytes, or authorize an unsupported release claim. Passing quality checks likewise does not approve a PROPOSE_ONLY product, brand, domain, direction, system, promotion, or release decision.

Route a downstream finding as follows:

1. Identify the exact affected target revision, criterion, evidence or uncertainty, affected action, and each dependency edge or downstream consumer it touches.
2. Locate the earliest artifact whose content must change. File a revision request against its owner with the finding and affected exact locks. Use `system-request` only if the requested change is a system capability, token, component, pattern, layout, rule, or other system change. A product, brand, domain, or direction correction follows that artifact's owner and review path.
3. Propose a **new upstream revision**, preserving the approved snapshot and its decision history. Review the proposal through its applicable Human Commit Point. Continue safe provisional work under labeled assumptions while the decision is pending.
4. Assess downstream impact using each locked dependency's `onChange` minimum (`none`, `validate`, `revise`, or `invalidate`). Recheck affected criteria and evidence against the new upstream revision. A new downstream revision explicitly adopts the new exact upstream revision and verified digest; no dependency upgrades itself.
5. Record the reassessment and remaining `FAIL`, `CONCERN`, or `UNVERIFIED` states before any affected merge or release. A rejected revision remains rejected history; a later attempt is a new proposal with the rejection context.

The Run state follows [9UI-89's priority](orchestrator-runs.md): `review-ready` if any valid proposal set remains ready; else `active` if any authorized reversible action remains; else `blocked` if an unresolved blocker remains; else `closed`. A `BLOCKER` finding on one task does not displace a valid ready proposal or stop independent safe work. No safe work and an unresolved prerequisite yields `blocked` with its reason. Final release still requires explicit human approval and an evidence account in the [Design Package quality inventory](design-package-governance.md).

## Worked decisions

| Situation                                                                                                           | Quality record                                                                                                                                         | Affected action and next route                                                                                                                                                                                           |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| An artifact fails its JSON Schema, or its exact dependency digest differs from the locked revision.                 | Deterministic `FAIL` / `BLOCKER`, with validator output or verified mismatch tied to the exact revision.                                               | Block use, proposal merge, and release of that artifact or dependent set. Correct a provisional draft or propose a new revision; verify the lock before reassessment. Other independent work can continue.               |
| Axe passes on one desktop prototype page, but keyboard, focus, dynamic states, and mobile manual checks are absent. | Automated-rule criterion may be `PASS` with scope and report; full WCAG 2.2 AA assessment is `UNVERIFIED`, with severity reflecting the affected risk. | Continue scoped provisional work. Do not assert conformance or release on the automated result alone; perform the applicable manual and human checks.                                                                    |
| A critical flow is claimed usable by a high-risk population without observation or adequate source evidence.        | Empirical usability claim is `UNVERIFIED` / `BLOCKER` for a decision relying on it, with the proposed study and population gap stated.                 | Block that dependent durable choice or release claim; continue safe prototype and study preparation. Approval cannot substitute for the missing observation.                                                             |
| A required mobile flow hides the primary action and loses entered state, although its layout fits the screen.       | Mobile primary-goal parity is `FAIL` / `MAJOR` or `BLOCKER` according to the task impact, supported by an exact mobile scenario.                       | Revise the affected flow and any upstream rule or layout that caused it; retest goal completion before its affected merge or release.                                                                                    |
| Three candidate directions vary only in color and typography while retaining the same task structure.               | Structural diversity is `FAIL` / `MAJOR`; visual variation is acknowledged separately.                                                                 | Revise the direction set from distinct problem-relevant mechanisms before presenting it as divergent options for human selection.                                                                                        |
| Validation shows an approved Experience Domain boundary misroutes a cross-domain journey.                           | Journey continuity is `FAIL`, with evidence and exact approved domain and downstream revisions.                                                        | Request a new domain revision through its owner and human review, then explicitly adopt it in affected downstream revisions and reassess. Do not edit the approved domain or relabel the critique as a `system-request`. |

## Implementation boundary

[9UI-88](https://linear.app/9uile/issue/9UI-88/) owns artifact schemas and their structural checks. [9UI-89](https://linear.app/9uile/issue/9UI-89/) owns Run transitions and commit guards. [9UI-90](https://linear.app/9uile/issue/9UI-90/) owns Skill invocation envelopes. [9UI-95](https://linear.app/9uile/issue/9UI-95/) owns package governance. [9UI-96](https://linear.app/9uile/issue/9UI-96/) and [9UI-120](https://linear.app/9uile/issue/9UI-120/) own tooling and CI implementation. Later quality implementations such as [9UI-108](https://linear.app/9uile/issue/9UI-108/) and [9UI-113](https://linear.app/9uile/issue/9UI-113/) can consume these criteria without treating this document as an executable validator.

Current schemas provide no dedicated structured field for conditions, affected action, evidence-to-finding linkage, or revision-request identity. Use permitted prose, narrow provenance, associated validation artifacts, and review records to preserve those semantics. If an implementation needs machine-enforced traceability, propose a separately reviewed contract change through the owning schema work; do not silently add fields or pretend that existing validators enforce the semantic obligations above.
