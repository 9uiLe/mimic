# 色の知識とDesign Token — 方向確認の小案

これは色の知識とDesign Tokenを一緒に構成した初稿時の記録で、未採用の編集用下書きです。候補の章立てと例はMimicによる整理で、単一の確立した色彩理論ではありません。
方向確認に使った時点の説明案を残しています。現在の色の提示方針は[利用ガイド](../../guideline/README.md#uiの色を具体的に示すとき)、色の読む道筋は[「色の知識」の案内](../../topics/color.md)、値の共有の仕組みは独立した[Design Tokenの本文](../../knowledge/design-tokens/KNOWLEDGE.md)、本文全体は[知識の索引](../../knowledge/README.md)を参照してください。この下書きを現在の方針や本文の代わりには使いません。

## 目的・完成条件・確認方法

- **目的：** UIの色を、見た目の印象・読める条件・意味・継続して管理する仕組みをつないで説明する。
- **今回の完成条件：** 追加候補、短い説明、Tokenを使う色の例から、次に書く知識の方向を判断できる。
- **確認方法：** 定義と出典の対応を照合し、説明上の整理と作例を区別する。数値の確認は対象の前景・背景・状態を固定して行う。
- **この下書きの範囲：** 方向確認に使った小案。以下の説明と作例は、現在の個別本文の正式採用を示すものではない。

## 決定した方向

UIでの判断に使える基礎と設計思想を優先し、歴史上の思想家・美術教育の体系は後の候補とする方向に決定した。
具体的なUI色の説明・提案では役割Tokenを前提にし、値または参照先、用途、組み合わせる背景や必要な条件を示すことも、Mimic共通の方針として確認済みである。
最初の３概念は採用前（`proposed`）の個別本文へ進めた。方向への同意と、完成した説明文の正式採用・公開は区別する。

## 追加する知識の候補

以下は方向確認時の６候補である。現在は「明度と相対輝度」「色コントラスト」「Design Token」の３件を採用前の個別本文に整理し、残る３件は後続候補としている。

| 候補と配置案 | 中心となる問い | 区別して説明すること |
| --- | --- | --- |
| 明度と相対輝度 `lightness-and-luminance` | 「明るい」とは何を指すか | 知覚上の明るさ・色空間の明度・WCAG計算上の相対輝度 |
| 色の対比と文脈 `color-context` | 周囲の色で見え方はどう変わるか | 相互作用の説明と、規格に基づく数値評価 |
| 色コントラスト `color-contrast` | 何と何の差を、どの目的で評価するか | 文字・非テキスト・装飾の条件と、基準の適用範囲 |
| 色による意味と情報 `color-and-meaning` | 色が何を伝え、色以外の何が必要か | 役割の一貫性、文化や慣習への依存、色だけに頼らない伝達 |
| 色空間と色域 `color-spaces` | 数値をどの表現・表示範囲で扱うか | sRGBなどの表現と、明度等を扱う色空間の特性・限界 |
| Design Token `design-tokens` | 設計上の意図と値をどう共有するか | 名前・型・値・参照、paletteと役割、テーマによる割り当て |

この順は当初の学習案で、原典の正式な分類ではない。最初に個別本文へ進めたのは「明度と相対輝度」「色コントラスト」「Design Token」。
「色の対比と文脈」は視覚知覚や色彩教育の原典を確認してから広げる。普遍的な配色の正解として提示しない。
現在は[「色の知識」の案内](../../topics/color.md)と独立した[Design Tokenの本文](../../knowledge/design-tokens/KNOWLEDGE.md)から参照する。
既存の[視覚的な優先順位](../../knowledge/visual-hierarchy/KNOWLEDGE.md)とは、色による強調と情報の重要度を混同しない点で接続する。

## 短い説明の見本

以下は確認した公式資料を基にした説明案であり、まだ採用済みの知識本文ではない。

「明るい色にする」だけでは、何を変えたいかが曖昧です。人が感じる明るさ、色空間で表す明度、コントラスト計算に使う相対輝度を区別します。
たとえばWCAGのコントラスト比は、前景と背景の相対輝度の組み合わせを扱います。色名や色相の違いだけでは、その比は決まりません。

読みやすさを考えるなら、文字色だけを選ばず、文字の大きさ、背景、状態も確かめます。数値基準に適合することと、実画面で十分に読みやすいことは確認対象が異なります。
また、警告を赤くする場合も「警告」という文言やアイコンを組み合わせ、色だけで意味を伝えない説明へつなぎます。

Design Tokenは、設計判断を共有するための、人が読める名前と値を持つものです。色のほか、余白や文字に関する値なども対象になります。
aliasは、値を直接書く代わりに他のTokenを参照する仕組みです（[DTCG Format §3.1・§7](https://www.designtokens.org/tr/2025.10/format/)）。
この意図を管理するため、例では `color.text.primary` のような役割Tokenを入口にします。
役割Tokenは「本文の主要文字」という用途を表し、paletteのどの値を使うかをテーマごとに割り当てます。
同じ値を使う役割でも、将来同時に変えるとは限りません。値の一致だけで意味の異なる役割をまとめる必要はありません。
Tokenの名前を付けたことだけで、配色の適切さやアクセシビリティの検証が済むわけではありません。

## 設計思想として読む見本

**色の見分け方が異なる人にも伝達を開く。** [WCAGの色の使用](https://www.w3.org/TR/WCAG22/#use-of-color)は、情報等を伝える唯一の視覚的手段に色を使わないことを求めます。
ここではその立場を、色以外の文言・形・構造も使って意味を伝える思想として説明します。この見出しはMimicによる言い換えです。

**個々の色値より、役割と関係を保つ。** [Carbonの色設計](https://www.carbondesignsystem.com/building-blocks/foundations/color/overview)は、themeを変えても役割を保ち、割り当てる値を変える仕組みを説明します。
この立場なら「この青を使う」に加えて「主要操作を示す役割をどの背景で担うか」を考えます。Carbon固有の設計思想の紹介であり、普遍的な配色理論としては扱いません。

## Tokenを前提にした色の提示例

作成した説明用の例。ライトテーマ・通常状態・不透明な単色背景の本文に対象を限定する。
値や名前はMimicの作例であり、特定製品の推奨paletteでも、DTCG規格の必須階層でもない。

| 役割Token | paletteへの参照 | 参照先の値 | 用途と組み合わせ |
| --- | --- | --- | --- |
| `color.surface.canvas` | `palette.neutral.0` | `#FFFFFF`（sRGB） | 本文が載る画面の背景 |
| `color.text.primary` | `palette.neutral.900` | `#1A1A1A`（sRGB） | canvas上の主要な本文 |
| `color.text.secondary` | `palette.neutral.600` | `#595959`（sRGB） | 同じcanvas上の補助文 |

参照の読み方は `color.text.primary → palette.neutral.900 → #1A1A1A`。
ここでのドット区切りは説明用の表記で、特定の交換ファイル形式を示すコードではない。
背景を変えるときは前景との組み合わせを再確認する。ダークテーマでは役割を保ちながら割り当てを変える案を検討する。
paletteの段階名だけから明度差やコントラスト比が等間隔だとは解釈しない。

**提示条件：** 用途＝本文、背景＝canvas、状態＝通常、テーマ＝light、透明度＝1。
**数値確認済み：** canvas上でprimaryは約17.40:1、secondaryは約7.00:1。W3CのsRGB相対輝度式とコントラスト比の式で算出した。
丸め前の値は17.404327532742:1と7.004729208036:1で、どちらも通常文字の4.5:1以上という色対の数値条件を満たす。
**未評価：** 文字サイズ・太さ、実画面の読みやすさ、hover・disabled・focus、dark、透過や画像背景、色覚差、表示環境。
確認したのはこの文字色対の数値だけで、実画面の評価やWCAG全体の適合は未確認。背景や透明度などの条件が変われば再計算する。

## 出典と確認の状態

2026年10月22日の分担調査で以下の公式資料を確認した。説明候補のすべてを裏付けた状態ではない。
6件への分割、学習順、Tokenの名前・値・表の書式はMimicの説明案である。

| 説明案の主張 | 確認した出典と箇所 | 適用範囲・注意 |
| --- | --- | --- |
| 色表現の明度を同一視しない | [CSS Color 4](https://www.w3.org/TR/css-color-4/#the-hsl-notation) §7・§9.1・§9.4 | HSLのL、知覚的な明度、相対輝度を混同しない。色彩心理の普遍則ではない |
| 前景・背景の相対輝度から比を求める | [Understanding Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html#dfn-contrast-ratio) 定義 | WCAGの公式参考解説。比の計算だけで実画面の読みやすさを保証しない |
| 文字のコントラストを条件付きで扱う | [WCAG 2.2 §1.4.3](https://www.w3.org/TR/WCAG22/#contrast-minimum) | 通常文字4.5:1、大きな文字3:1。大きな文字の定義と例外を含めて適用する |
| 非文字情報の識別に必要な差を扱う | [WCAG 2.2 §1.4.11](https://www.w3.org/TR/WCAG22/#non-text-contrast) | 対象のUI・状態等を識別する情報と隣接色の3:1。全境界線に一律適用しない |
| 色以外にも情報を伝える手段を持つ | [WCAG 2.2 §1.4.1](https://www.w3.org/TR/WCAG22/#use-of-color) | 情報や操作等を伝える唯一の視覚的手段に色を使わない |
| Tokenは名前を持つ値を表し、参照できる | [DTCG Format 2025.10](https://www.designtokens.org/tr/2025.10/format/) §3.1・§7・§7.1.1 | Community Groupの最終報告。W3C標準ではなく、作例の役割命名を強制しない |
| 役割を保ち、theme間で値を割り当てる | [Carbon — Color overview](https://www.carbondesignsystem.com/building-blocks/foundations/color/overview) Color anatomy・Implementing color・Themes | Carbonの設計思想。中立色の構造・青の主要操作など製品固有の判断を普遍化しない |

既存本文は「視覚的な優先順位」v1.0.0（accepted）の本文・出典表・説明例を確認した。
そこでの視覚的な強調と業務上の優先度の区別は、色の新たな原典を確認したこととは区別する。
周囲の色による知覚、歴史上の思想、文化を超える色の意味、CIE用語の厳密な訳語は未調査。
色空間と色域の個別記事には、公式仕様との対応をさらに整える必要がある。

## 今後の判断

基礎から役割Tokenへつなぐ方向と共通の提示方針は確認済みである。個別本文の正式採用と公開は、それぞれ対象の本文・差分を確認して判断する。
