# 変更の根拠と品質検査

変更の入力・期待結果・根拠・未確定事項を、実装やテストの出力とは独立して残します。機械検査の成功は、仕様や命名の意味を採用したことにはなりません。知識本文の意味と根拠は[運用方針](README.md)に従います。

## 確定した検査条件

800行・200文字、固定した導入前の版、indexのみを読むhook、基準の緩和を別途レビューすることは、利用者が指定した検査要件です。数値・対象・限定した禁止名・除外理由の正本は [.quality/policy.json](../.quality/policy.json) です。

行数は空行・コメントを含む全文を数えます。最後の改行だけでは空行を増やさず、LFまたはCRLFを改行として扱います。行長は改行を除くUnicodeコードポイント数です。UTF-8として読めない対象、構文を解析できない対象、必要ツールや比較元の不足、想定外の空集合は失敗です。

対象はGit管理下と非ignoreの新規手書きコード・テスト・検査スクリプト・設定です。既存の `.agents/` 内のPythonも含めます。拡張子のないhookなどは `included_paths` で明示します。未知の形式は黙って対象外にせず、コードか、それ以外かの分類を要求します。依存コードと作業出力はGitのignore対象です。生成された違反基準JSON、ロックファイル、知識・説明のMarkdownなどの扱いと理由はpolicyを参照します。手書きHTMLは除外しません。

現行の生成物は `_site/`・`output/` に置き、Git管理の対象にしません。policyに残る旧生成HTML２件の除外は、固定した初期基準を再現するために保持します。現在の生成物をRepositoryへ戻すための指定ではありません。

## 固定した根拠と既存違反

導入前の確定版は `85f3962e0c17680782574403785121a4b2f194f6` です。[基準](../.quality/baseline.json)の `initial` は、このコミットのGitオブジェクトから計測した記録であり、作業ファイルから作り直しません。未コミットの違反や、後からコミットされた新しい違反を追加の免除にしません。

初期記録には800行超のファイルはなく、200文字超は15行、限定禁止名は1箇所あります。ファイル名・該当行・計測値・元の行を基準に残します。既存違反の全修正は要求せず、悪化を止めます。

長いファイルの免除は初期記録にある由来だけに認め、基準の上限・比較元の実際の長さの小さい方を使います。縮小を基準へ反映したら元の長さへ緩和できません。800行以下になれば通常の上限へ戻します。ローカルはHEAD、CIは取り込み先の確定SHAを比較元にします。

長い既存行は同一の内容だけを維持・移動できます。既存行の総数を割り当て、コピーで免除を増やしません。変更行は200文字以内にします。Gitで確認した改名は元の由来を引き継ぎ、コピーは新規です。対応が分からない改名を推測で免除しません。改名や改善時には次の明示コマンドで基準を縮小し、その差分もステージします。

```sh
bun run quality:ratchet
```

この操作は免除の追加や上限の増加をしません。hookは基準を更新しません。改善や改名を基準へ記録し忘れた場合も検査は失敗し、このコマンドを案内します。基準の永続的な改善は、そのJSONの更新とコミットで引き継ぎます。

## 名前と仕様の判断

PythonとTypeScript/JavaScriptの宣言は構文木で調べ、文字列や外部APIのプロパティ名と区別します。機械検査はpolicyの限定禁止名だけを判定します。新設・改名ファイルの単独の `utils`・`types`・`config`、追加・改名識別子の `data`・`tmp2`・`a1` などを見直す対象にします。既存の禁止識別子は元の宣言とscopeを追跡できる場合に保留し、別の宣言へ置換された場合は再命名を求めます。宣言の意味が同じかはレビューで確認します。ツールの固定名や互換性が必要な例外は、対象と理由をpolicyに記載し、追加時はレビューします。

名前が業務上の役割を表すか、接頭辞を足しただけでないか、他言語の識別子や業務仕様が正しいかは、人が差分で確認します。コードとテストしか根拠がない説明は「現状の記録」です。未確定の仕様を「確定」に書き換えません。

変更したコードと根拠・検証方法の対応は [.quality/change-contracts.json](../.quality/change-contracts.json)、代表処理の具体的な入力と期待値は [.quality/behavior-cases.json](../.quality/behavior-cases.json) に置きます。対応の存在を機械検査し、その内容の正しさは別にレビューします。[テストの根拠と故障検出](test-evidence.md)に、固定テストで意図的な誤りを検出する手順があります。

## 手元での実行

[Nix環境と依存の導入](development.md#環境と基本手順)の後に実行します。Python 3とBun、固定版のTypeScriptが必要です。検査中に依存を自動導入しません。

```sh
bun run quality:check
bun run quality:test
bun run test:effectiveness
bun run build:pages
bun run verify
```

`quality:check` は新規ファイルも含む全体検査です。検査設定・除外・基準・スクリプト・hook・CI・既存テストの変更は、パスと変更前後のSHA-256を別枠で出力します。必要なら `--report output/quality/check-report.json` で記録できます。数値の緩和、対象の削減、例外の追加、固定比較元の変更は通常の更新として通しません。検査コードやテスト自体の妥当性は、この報告と `git diff <比較元> -- <対象>` を使ってレビューします。

## pre-commit

通常セットアップで、リポジトリ内だけのhookを設置します。

```sh
bun run setup:hooks
bun run quality:staged
```

installerはGitが示す実際の配置先を使い、グローバル設定を変更しません。未知の既存hookやリポジトリ外の共有配置先を上書きしません。その場合は既存処理を読んで統合方針を確認します。

設置した小さなbootstrapは、index内のhook・検査スクリプトを読み、indexの全文・設定・基準・helperを一時スナップショットへ取り出して共通検査へ渡します。未ステージの修正は合否に混ぜません。`GIT_INDEX_FILE`、部分ステージ、NUL区切りのパス、初回コミットを扱います。競合、必要ファイルの削除、読取失敗は非ゼロです。対象コードの変更がない正常終了と、検査不能は区別します。同じGit共通ディレクトリを使うworktreeにもhookが及ぶため、導入ファイルのない古いブランチでは検査不能としてコミットを拒否します。

通常はステージされた対象コードを検査し、検査条件やhook・CIなどの変更時はindex内の全対象を再検査します。削除したファイルの本文を読まず、改名を比較元へ対応付けます。hookは整形・ステージ・stash・resetをしません。重いテストと意図的な誤変更は専用コマンドかCIで実行します。

導入ファイルがまだindexにない場合は検査不能としてコミットを拒否します。導入時の実起動確認には、一時的な別indexへ候補を登録できます。利用者の通常indexを書き換える必要はありません。

## CIと共有設定

[Repository Quality](../.github/workflows/quality.yml)は、PRのhead SHAと取り込み先のbase SHAを固定し、候補コミット全体の共通検査・検査器のテスト・代表の故障検出・既存verifyを実行します。取り込み先に検査器がある場合は、CIの起動処理からその版を取り出し、取り込み先の検査器で候補を判定します。ローカルの `quality:ci --base <SHA> --commit <SHA>` も同じ検査器を選びますが、起動スクリプト自体の変更は別途レビューします。初回導入は比較元に検査器がないため、その事実を表示し、導入差分の人によるレビューを必要とします。

ローカルhookは迂回できます。候補側が変更できるworkflowだけでも、workflow自体の弱体化を完全には防げません。検査・設定・基準・期待値の差分は自動で採用せず、根拠と影響を確認します。

リモートで取り込みを止めるには、`main`の取り込み保護で `Repository Quality / repository-quality` を必須チェックにし、検査条件・workflowの変更を独立したレビュー対象にする設定が必要です。Rulesetの必須workflowやCODEOWNERSによる保護は、組織の権限・契約・レビュー担当によって設定します。担当者は未確定です。リモートへのpush、PR作成、取り込み保護の変更は、差分・検査結果を提示した後の許可対象です。

CIファイルの作成、ローカルでのCI相当検査、hookの有効化、GitHub上での実行、必須チェック設定の適用は、それぞれ別の完了事項として報告します。
