# AI向けの作業ガイド

この文書は、Repositoryの内容・機能・運用を変更または点検するAIの作業指示です。知識の検索・参照・説明だけを行う場合の入口は[知識の索引](../knowledge/README.md)です。Repositoryの作業を始める前に、[Repositoryの方針と利用ガイド](README.md)を全文読みます。同文書が運用方針の正本です。会話に依存せず、Repository内の現在の方針と文書の状態を確かめて進めます。

## 目的を維持する

Mimicは、デザインの知識・概念・思想・哲学を言語化して説明する知識データベースである。利用者から別の明示指示がない限り、独自の設計方式の研究や、画面の効果測定をRepositoryの目的に置き換えない。

知識の参照、説明の編集、知識の追加、個別UIへの適用、生成・配信機能の変更を区別し、依頼された作業の範囲を保つ。

## 参照してから説明する

知識の入口 `knowledge/README.md` は、概念の一覧と独立した意味付き関係グラフへ案内する。`relations/graph.json` の根拠付きの辺と `relations/vocabulary.json` の型・方向・推移規則を使い、目的に応じて索引する。読む順序・範囲は読むAIが判断し、固定手順や必読の概念集合は設けない。

説明に使う概念の `KNOWLEDGE.md` と必要な出典・例は実際に読む。本文は概念の説明正本、関係データは構造化関係の定義元であり、索引、グラフ、題名、リンク先を見ただけで本文を確認済みと報告しない。未記載の関係を無関係と解釈せず、型の意味を超えた逆向きや推移を推定しない。具体的な契約は[関係グラフの案内](../relations/README.md)を参照する。

`topics/` の横断的な案内や、その生成ページは、個別概念の本文を読んだ代わりにはならない。説明に使う概念の入口と必要な補足を実際に読む。

参照する本文の版・対象範囲と必要な出典を確認する。閲覧ページや公開URLの存在から、説明の根拠や正確さを推測しない。

出典の内容に触れるときは、対応する原典や公式資料の該当箇所を確認する。確認できない主張は、知識として確定しない。提唱者の主張、対象範囲、説明上の言い換え、作成した例を区別する。複数資料をまとめた章立てを、単一の確立した理論や原典の分類として扱わない。

色の知識を参照するときは[「色の知識」の案内](https://github.com/9uiLe/mimic/blob/main/topics/color.md)から必要な本文へ進みます。値を共有する仕組みは、色とは独立した[Design Tokenの本文](https://github.com/9uiLe/mimic/blob/main/knowledge/design-tokens/KNOWLEDGE.md)を読みます。版・対象範囲と出典を確認して使います。具体的なUI色の提案や配色例では、[利用ガイドの色の提示方針](README.md#uiの色を具体的に示すとき)を適用します。

具体的なUIの文字スタイルを提示するときは、[利用ガイドのTypographyの提示方針](README.md#uiのtypographyを具体的に示すとき)を適用します。

視覚的な説明が必要なときは、[整列とグリッドの本文](../knowledge/alignment-and-grids/KNOWLEDGE.md)と[整列の説明図](../knowledge/alignment-and-grids/examples/alignment.svg)、[色の文脈の本文](../knowledge/color-context/KNOWLEDGE.md)と[色の相互作用の説明図](../knowledge/color-context/examples/surrounding-colors.svg)を参照します。
本文から例の文章も読み、図が示す関係と対象範囲を確認します。図の見た目を、普遍的な最適解や効果の実証として扱いません。

## 知識を編集する

定義、背景、概念同士の違い、適用範囲、出典との対応を説明する。具体的な案件の採用案や、AIが考案した手順の有効性を、既存知識として記載しない。

知識の意味を変える必要があるのか、説明の不足や曖昧さを直すのかを判断する。AIの読み違いがある場合は、本文の表現と原典を照合し、定義・補足・例を修正する。別のAIによる校読は、文章の解釈を確認する作業として扱う。知識そのものの有効性を実証した結果とは報告しない。

不明な点を推測で埋めて知識本文へ反映しない。調査中の主張や作業上の仮定は、原則としてGit管理外の `output/` の下書き・作業メモに残し、正本の知識と区別する。説明用の例を作る場合は、概念の説明に必要な範囲にとどめ、実験で得た効果や一般的な最適解のように書かない。

依頼の範囲で原典と主張の対応、対象範囲、説明用の例との区別を確認し、知識を追加・改善する。根拠や方向に未解決の点がある場合は、小さな説明案で確認し、調査メモを正本へ混ぜない。本文と版を更新し、生成物がある文書は編集元だけを編集して再生成する。本文を変えた場合は、それを根拠にする関係の意味・適用範囲・引用を再照合してから `bun run relations:sync` で本文メタデータとSHA-256を同期し、`bun run relations:check` で検査する。同期は意味辺を修正せず、検査成功は関係の意味の正しさを保証しない。

## 人への確認を絞る

調べられる事実を先に調べ、目的・選好・採否などの不明点を成果への影響で優先する。一度の質問は３つ以内にし、専門知識が必要な問いには選択肢、おすすめ、理由、欠点を添える。

答えられない点は仮案とその仮定を提示する。確認が不要な細部は判断して進める。回答に依存しない調査や下書きを続ける。人が既に決めた内容や許可済みの操作を、未決定として聞き直さない。

## 確認の対象を合わせる

知識の編集では、原典との一致、定義や関係の明確さ、誤読の原因、例の位置づけを確認する。画面の試作や利用者による効果測定を、知識の掲載条件に追加しない。

生成器・リンク・公開範囲などを変更する場合は、その機能の検査を行う。検査の成功を、デザイン知識の正しさや使いやすさの実証へ拡大しない。

目的、完成条件、確認方法を短く示す。作業後は、変更の目的、実際に確認した対象と結果、未確認事項を分けて報告する。予定、推測、未実施の検査を、確認済みとして記載しない。

## 閲覧UIを変更する

Mimicの閲覧UIには[デザインシステム](design-system.md)を適用する。Tokenは`design/tokens.json`、疑問から知識を探す案内は`design/reading-paths.json`を編集し、生成CSSやHTMLを直接直さない。原則・部品・状態・例外を実装と整合させる。7つの疑問を正式な概念分類や必読順序と呼ばず、知識の原題・本文・引用・関係の意味を変えない。同じ閲覧対象は「知識」と呼び、正本にある固有の専門語や引用は保つ。

## 操作の許可と公開

公開・外部への送信・削除・費用発生・稼働中の環境変更は、対象と操作の許可を実行前に確認する。現在の依頼で既に明示的な許可がある場合は、その範囲で実行し、再確認しない。

`main` へのpushはGitHub Pagesの公開操作を伴う。公開対象と差分を確認し、許可された文書だけを反映する。別の外部操作はそれぞれ許可された範囲で行う。

## 作業場所と更新

運用方針は `guideline/README.md`、AIの作業指示はこの文書、デザイン知識は `knowledge/<概念ID>/KNOWLEDGE.md` とそこから参照する補足、構造化した関係と関係型は `relations/` のJSONを正本として扱う。[知識の構造ガイド](https://github.com/9uiLe/mimic/blob/main/guideline/knowledge-structure.md)に沿って、一つの概念・思想・哲学を一つのディレクトリに置く。同じ説明を複数箇所へ独立に追加せず、横断的な案内は `topics/` から参照でつなぐ。

この構造は知識資料の配置であり、スキルの実行契約ではない。`SKILL.md`、起動トリガー、ツール許可などを知識の入口へ追加しない。補助スクリプトがある場合も、知識を読むだけで実行しない。方針を変更したときは、人向け説明・AI向け指示・入口・生成と公開の振る舞いの食い違いを確認する。

READMEは、その場所の目的、現在の内容、読み方・使い方への入口として編集する。変更履歴、作業の進捗、個々の確認結果をREADMEへ追加しない。変更理由と確認結果はPRに記載する。生成物の更新・検査・公開では[開発・公開ガイド](https://github.com/9uiLe/mimic/blob/main/guideline/development.md)を参照する。
