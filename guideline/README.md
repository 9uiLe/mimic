# Repositoryの方針と利用ガイド

Mimicは、デザインの知識・概念・思想・哲学を言語化し、人とAIが理解できるように説明する知識データベースです。デジタルUIに関する知識を扱います。

この文書はRepositoryの運用方針の正本です。[AI向けの作業ガイド](ai.md)は、Repositoryを変更または点検するAIの作業指示です。知識の検索・参照・説明の入口は[知識の索引](../knowledge/README.md)です。デザイン知識は `knowledge/` に、一つの概念・思想・哲学につき一つのディレクトリを用意し、固定の入口 `KNOWLEDGE.md` を置きます。

本文から独立した[意味付き関係グラフ](../relations/README.md)を `relations/` に置きます。概念の説明正本は本文とその補足、構造化した関係の定義元は `relations/graph.json`、関係型・方向・推移規則の定義元は `relations/vocabulary.json` です。AIはこれらを索引として使い、目的に応じて読む順序・範囲を決めます。固定の順序や必読集合を課しません。説明に使う本文と必要な根拠は実際に確認します。

## 掲載する内容

既存の知識や概念を、意味・背景・関連する考え方とともに説明します。原典、提唱者の解説、公式指針などを確認し、出典が述べている範囲に沿って記述します。

理論・思想・哲学は、提唱者や立場、成立した背景が分かるように説明します。その立場の主張を、すべての場面で成立する事実へ置き換えません。適用範囲や他の考え方との違いも、知識の説明に含まれます。

未確定の仮説、独自の設計手順、案件固有の仮定を、共通知識として掲載しません。出典からの説明を超える提案は、編集用の下書きで扱います。仮定を明記したことだけでは、知識として確かめたことになりません。

## 説明の品質と掲載

掲載に向けて、次を確認します。

- 定義、背景、関連概念との違いが、原典の意味に沿っている。
- どの主張をどの出典で確認したかが分かる。
- 出典の主張、日本語での説明、説明用に作成した例が混同されない。
- 対象範囲や立場が明確で、独自の仮説を一般則にしていない。

AIが読み違えた場合は、どの表現が誤解を招いたかを確認し、文章や補足説明を修正します。知識の意味を保ちながら、定義・例・関連概念の説明を整えます。原典の読み違いや誤記が判明したときは、根拠を確認して内容を訂正します。

画面の試作、発見率、作業時間などの効果測定は、知識を掲載するための一律の条件にしません。個別のUIの使いやすさや配信機能の動作を確認するときに、その対象に応じて行います。

## UIの色を具体的に示すとき

UIの色を提案したり、具体的な配色例で説明したりするときは、用途を表すDesign Tokenの役割名を前提にします。値または参照先と、用途・組み合わせる背景を示し、状態・テーマ・透明度など結果に影響する条件も併記します。

既存のTokenが示されている場合はそれを使い、不明な場合は説明用の仮名であることを明記します。架空の正式なToken体系を作りません。歴史的な説明や原典の引用にある色表現には、無理にTokenを当てはめず、具体的なUIへの提案と区別します。

Token名やコントラスト比などの数値だけで、配色の適切さやアクセシビリティを保証しません。この方針は、色の知識の定義や分類ではなく、Mimicで具体的なUI色を提示する方法を定めます。色の基礎は[「色の知識」の案内](https://github.com/9uiLe/mimic/blob/main/topics/color.md)、値を共有する仕組みは独立した[Design Tokenの本文](https://github.com/9uiLe/mimic/blob/main/knowledge/design-tokens/KNOWLEDGE.md)を参照します。

## UIのTypographyを具体的に示すとき

具体的なUIの文字スタイルを提案・説明するときは、本文・見出しなど役割を表すDesign Tokenを前提にします。書体・文字サイズ・太さ・字間・行高を一組として示し、基礎Tokenへの参照も必要に応じて説明します。値が同じことだけを理由に、異なる役割を一つにまとめません。

既存のTokenを優先し、不明な場合は説明用の仮名と明記します。対象言語、書体と代替書体、表示領域、文字サイズ変更への対応など、組み合わせを判断する条件を添えます。原典の数値や歴史的な説明と、具体的なUIへの提示は区別します。

Tokenの組と値だけでは、実際の字形・折返し・拡大時の表示を保証できません。具体的な作例は[Typographyの説明例](../knowledge/typography/examples/mixed-ui-copy.md)、共有の仕組みは[Design Tokenの本文](../knowledge/design-tokens/KNOWLEDGE.md)を参照します。この提示方針はMimicの編集方針であり、DTCGの必須命名や全用途の要件ではありません。

## Mimic閲覧UIへの適用

MimicのGitHub Pages閲覧UIでは、[デザインシステム](design-system.md)を適用します。Tokenは`design/tokens.json`、疑問から知識を探す案内は`design/reading-paths.json`で管理します。白黒主体の表示、同じ対象を「知識」と呼ぶ表現、本文・関係・出典を行き来する共通の操作を定めます。これは案件固有の適用規則であり、知識本文に書かれた一般概念や全製品への推奨値ではありません。

5つの疑問は閲覧のきっかけであり、正式な概念分類や必読順序にしません。読者は一覧・本文・関係からも読む範囲を選べます。方向の採用、機械検査、実操作の確認、人による理解、読み上げは別の確認として扱います。

## 下書きと正本

一時的な調査メモ・下書き・個別UIの検証記録は、原則としてGit管理外の `output/` に置きます。正本に反映した下書きや完了した作業記録は現行ツリーに常設せず、既にGit管理されたものは履歴から参照します。知識本文・出典対応表・説明例は正本として保持します。

知識の追加や改善では、原典と主張の対応、対象範囲、説明用の例との区別を確認して正本を更新します。既存の説明も必要に応じて改善し、不要な記述は通常の編集として整理します。根拠や方向に未解決の点があるときは、小さな説明案で確認し、仮説を確定した知識として扱いません。

文書の版・対象範囲は、各知識本文の先頭で確認します。AIは正本Markdownを読み、必要な出典と補足をたどります。Pagesは人が読むための表示です。機械検査の成功だけで知識の正しさは保証されません。

## 人とAIの進め方

AIは、資料から調べられる事実を先に確認します。人には、目的、選好、必須制約や、依頼だけでは決められない採否を尋ねます。成果への影響が大きい不明点から優先し、一度の質問は３つ以内にします。

専門知識が必要な質問には、選択肢とおすすめ、その理由と欠点を添えます。人が答えられない点には仮案を示し、作業上の仮定を明記します。確認が不要な細部は、おすすめの方法で進めます。その仮案や仮定を、知識の本文へ自動的に採用しません。

作業の目的、完成条件、確認方法を短く整理し、下書きや小さな例で方向を確かめます。作業後は、変更の目的、確認したこと、その結果、まだ確認できていないことを説明します。

## 実行前に確認する操作

公開、外部への送信、削除、費用の発生、稼働中の環境の変更は、実行前に人の許可を確認します。対象と操作について既に明示的な許可がある場合は、その範囲で進め、同じ許可を聞き直しません。許可の対象外へ範囲を広げません。

このRepositoryでは、`main` へのpushでGitHub Pagesが更新されます。公開を伴う反映として扱い、許可された対象と操作の範囲を守ります。

## 編集元と公開ページ

READMEは、そのRepositoryやディレクトリの目的、現在の内容、読み方・使い方を説明する入口です。必要な詳しい説明は専用の文書へリンクします。変更履歴、作業の進捗、個々の確認結果はREADMEに追記せず、PRや作業記録に残します。この文書は `guideline/` の案内と、Repositoryの運用方針を兼ねます。

この文書と[AI向けの作業ガイド](ai.md)はMarkdownを編集元とし、GitHub Pages用のHTMLを生成します。説明を変更するときはMarkdownを編集し、生成HTMLを直接編集しません。

[知識の入口](https://github.com/9uiLe/mimic/blob/main/knowledge/README.md)には、各概念の `KNOWLEDGE.md` と版の確認方法があります。入口から、出典を置く `references/`、必要に応じて用意する `examples/` や `scripts/` などの補足へ案内します。配置と役割は[知識の構造ガイド](https://github.com/9uiLe/mimic/blob/main/guideline/knowledge-structure.md)に定めます。スキルに似た資料の配置を用いますが、ClaudeやCodexのスキルとしての呼び出しや実行は定義しません。

複数の概念を横断する目的別の案内は `topics/` に置き、個別概念の本文を重複して持ちません。本文内の関係の説明は人向けの文脈として保持し、型・向き・適用範囲と根拠を持つ辺は `relations/` に定義します。両者が食い違う場合は本文と原典を照合して修正し、グラフの形に合わせて知識の定義を変えません。根拠のない階層や依存を補いません。

Repositoryの方針と閲覧UIの[デザインシステム](design-system.md)は `guideline/`、Tokenと入口の案内は `design/`、生成・検査は `scripts/`、閲覧UIのブラウザ処理は `web/`、配布フォントは `assets/`、検査とその根拠は `tests/`・`.quality/`、検査・公開処理は `.github/` に置きます。Pagesの共通CSSは`web/reading.css`で管理し、Tokenから生成する`web/tokens.css`の変数を参照します。`scripts/knowledge-view.css`は単体ローカルプレビュー用に保持します。編集・研究資料はGit管理外の `output/`、Pages生成物はGit管理外の `_site/` で扱います。配置の詳細は[知識の構造ガイド](https://github.com/9uiLe/mimic/blob/main/guideline/knowledge-structure.md)を参照します。

生成物の更新・検査・公開の手順は[開発・公開ガイド](https://github.com/9uiLe/mimic/blob/main/guideline/development.md)に記載します。
